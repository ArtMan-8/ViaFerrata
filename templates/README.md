# Как использовать шаблоны

Пакет поставляет семь библиотечных форм. Готовые документы принадлежат проекту; обновление пакета меняет формы для новых документов и не перезаписывает существующие.

| Документ | Форма                      | Когда создаётся                                          |
| -------- | -------------------------- | -------------------------------------------------------- |
| Intent   | [intent.md](intent.md)     | Вместе со Spec и Plan командой new                       |
| Spec     | [spec.md](spec.md)         | Вместе с Intent и Plan командой new                      |
| Plan     | [plan.md](plan.md)         | Вместе с Intent и Spec командой new                      |
| Journal  | [journal.md](journal.md)   | Агентом с началом Implement                              |
| SRS      | [srs.md](srs.md)           | Агентом при необходимости устойчивых требований продукта |
| Research | [research.md](research.md) | Агентом для исследования открытого вопроса               |
| ADR      | [adr.md](adr.md)           | Агентом для существенного долговременного решения        |

New создаёт ровно три документа: Intent, Spec и Plan. Наличие остальных шаблонов не требует создавать пустые артефакты и не добавляет команд CLI.

## Заполнение и optional-блоки

Команда `new` подставляет в три формы `{{change_id}}`, `{{date}}`, `{{title}}`. Остальные формы заполняет агент: для Journal использует ID текущего change, для SRS/Research/ADR заменяет `{{document_id}}` полным свободным ID соответствующего типа; дату и заголовок также заполняет фактическими значениями. Это подсказки формы, не дополнительные параметры new.

Необязательные YAML-поля закомментированы строками `# optional:` и `#`; примеры адресов не становятся активными ссылками. Необязательные разделы Markdown отмечены стандартными HTML-комментариями `<!-- optional: … -->`. Агент заполняет применимые части, удаляет неприменимые вместе с подсказкой и исправляет связанные ссылки. После удаления R или шага удалите либо обновите обращения к нему. Комментарии «Заполнение» поясняют содержание блоков: после заполнения удалите их, сохранив сам раздел. Комментарий optional разрешает убрать неприменимый блок; обычная подсказка такого разрешения не даёт.

Маркер optional не исключает следующее активное содержимое из проверки и не отменяет применимые требования профиля. Strict требует явных требований и связей. Оставшийся активный `TODO(VF)` вне архива даёт ошибку E_DRAFT_PLACEHOLDER, в архиве не проверяется; форма не подтверждает ни требования, ни согласование, ни успешную проверку. В готовых документах допустимы существующие адресаты и будущая цель корректной операции add в Changes.

## Назначение разделов

Context содержит сведения о проблеме, исходном состоянии, зависимостях и решениях, влияющих на понимание задачи. История поручений, создание ветки, основания разрешений и результаты проверок относятся к Journal; состояние исполнения — к Plan. До начала реализации Journal не создаётся ради служебной истории.

В Intent и Spec не повторяйте общие запреты и обязательства без специфического для задачи ограничения, исключения или существенного риска. Проверяйте, изменится ли понимание цели или контракта после удаления абзаца: несущественный служебный текст убирайте, содержательные основания и ограничения сохраняйте.

Для неформальных заметок используйте [правила и шаблон идей](../instructions/ideas.md). Они не добавляют формального типа документа к семи библиотечным формам.

Intent хранит цель, ограничения, контекст и AC с наблюдаемыми условиями и Verification. Examples перед Acceptance Criteria нужен только для уточнения результата. AC может покрывать требование задачной Spec или SRS; копировать AC в Spec не нужно.

Spec задаёт границы и проверяемые обязательства: поведение, форматы, ошибки, совместимость и инварианты. Scope добавляется для путей вне четырёх собственных артефактов. Предпочитайте узкие директории функциональной области; отдельные файлы указывайте для общих компонентов. Чтение смежного контекста не ограничено scope; необходимый рефакторинг допустим внутри принятого контракта и разрешённых путей. Выход за них согласуется до изменений. Protected_paths сохраняет запрет независимо от scope. Непустой protected_paths даёт E_UNSUPPORTED. Scenarios и дополнительные DOD нужны по смыслу; Given/When/Then — допустимая, но необязательная форма сценария. Неприменимый DOD не создаётся.

Plan содержит единственный checklist. Technical Approach нужен, если технические решения не раскрыты в шагах. Одной sequential-волны достаточно для простой задачи; дополнительные волны и parallel используются по необходимости. Волны идут последовательно. Depends on задаёт явную зависимость шага, не дублируя очевидный порядок. Отметка выполнения требует результата и применимых проверок. В Verification шага указываются недостающие практические детали выполнения проверки: тест, команда, фикстура, измерение, среда или ручная процедура. Если способ проверки уже достаточно конкретно описан в Intent или Spec, Plan ссылается на него.

Порядок тестирования задаётся в Plan независимо от lite/strict. Исправление дефекта начинается с воспроизводящего регрессионного теста; невозможность воспроизведения и альтернативная проверка фиксируются явно. TDD применяется, если выбран для задачи, и требует теста до соответствующей реализации.

Journal хранит точку продолжения, краткое основание согласования, существенные для текущего результата решения и фактические проверки. Полные копии других артефактов не требуются. V-блок появляется после реальной проверки, без заранее заполненного passed. В согласованном формате конечного состояния достаточно актуальных результатов с указанием входов и ограничений; хронология правок не требуется. Не ссылайтесь на локальные логи, снимки и манифесты, недоступные читателю репозитория; необходимые результаты и ограничения излагайте в Journal. Не указывайте абсолютные пути машины, временные установки и соседние проекты. Используйте команды от корня проекта, версии и идентификаторы проверенных входов. Различайте выполненный запуск, чужой отчёт и анализ кода. Итог должен учитывать последние разрешения и фактические повторы проверок.

SRS размещается в specs внутри documents_root и описывает устойчивую функциональную область. Обязательны Purpose and Boundaries, System Overview, Requirements с минимум одним R на H3 и Verification. Scenarios и приложения добавляются по необходимости. SRS хранит актуальные принятые обязательства и необходимый контекст, а Verification — устойчивые способы проверки, без текущих Passed/WIP. Одна SRS развивается через несколько changes; change может затрагивать несколько SRS или обходиться без них. Первоначальная SRS может позднее объединить принятые результаты нескольких changes с учётом последующих изменений; origin сохраняется в новой SRS, старые комплекты не переписываются.

### Дельта требований

В R задачной Spec одна операция относится к одному R SRS. Поля задаются непосредственными пунктами списка внутри H3 требования: `- Operation: add|modify|remove`, `- Changes:` с одним вложенным логическим адресом, `- Before:` и `- After:` с полным нормативным текстом редакции. Многоабзацный текст продолжается с отступом внутри пункта; заголовки требований в текст редакции не включаются. Для add требуется только After, для modify — Before и After, для remove — только Before. Неприменимое поле опускается. Комментарии, цитаты и примеры кода не образуют дельту.

Пример дельты приведён в [шаблоне Spec](spec.md#requirements).

Дельта определяется до исполнения. При modify сохраняется ID; самостоятельное обязательство получает новый ID. Remove отменяет обязанность, но не запрещает поведение. Отменённые ID требований не переиспользуются. Для новой SRS заранее задаются назначение, границы и будущие ID. Только Changes корректного add допускает отсутствующий адресат; обычная потерянная текущая ссылка остаётся ошибкой. Старый Changes без Operation не становится корректной дельтой автоматически: CLI сообщает о несоответствии формы.

Для новых Covers и Verifies предпочтительны собственные R Spec, фиксирующие переход; ссылки на SRS допустимы по смыслу. Исторический ID не доказывает редакцию на момент проверки. Правила применения и восстановления — в [жизненном цикле](../instructions/sync-and-archive.md).

Research размещается в research, ADR — в adr внутри documents_root. Стандартные названия и уровни разделов сохраняются. CLI проверяет обязательные H2 этих документов и Consequences/Confirmation внутри Decision Outcome ADR, но не полноту исследования или принятие решения. Ограничение CLI не отменяет обязательных разделов и правил заполнения.

Research обязательно содержит Research Question, Context and Scope, Method and Sources, Findings и Conclusion. Options and Trade-offs нужен при сравнении вариантов; Limitations and Open Questions — при существенных ограничениях или нерешённых вопросах; References — если нужен отдельный список источников. Существенные оговорки сохраняются независимо от наличия отдельного раздела. Method and Sources описывает метод и выбор источников, Findings связывает результаты с конкретными основаниями, References содержит библиографию. Источники доказательств не смешиваются с origin. Отрицательный результат и недостаток данных допустимы; completed означает завершение исследования, а не принятие рекомендации.

ADR обязательно содержит Context and Problem Statement и Decision Outcome, а внутри Decision Outcome — подразделы Consequences и Confirmation. В Consequences описываются существенные последствия. Confirmation задаёт постоянный способ проверки соблюдения решения; детали выполнения находятся в Plan, фактические результаты — в Journal. Considered Options нужен при рассмотренных альтернативах; искусственный второй вариант не добавляется. В Consequences сохраняются существенные последствия: положительный, отрицательный пункт и риск не обязаны присутствовать одновременно. Approved означает принятие решения, а не его реализацию.

Одна форма ADR содержит краткий вариант и расширения MADR. Для краткого варианта удалите необязательные Decision Drivers, Pros and Cons of the Options и More Information; Considered Options оставьте по применимости. Расширенный вариант раскрывает критерии выбора, аргументы по вариантам и дополнительные сведения. Все условные разделы и пункты отмечены optional; неприменимые блоки удаляются вместе с подсказками. При пересмотре принятого решения согласуются изменения к нему.

## Метаданные и отношения

ID определяет тип документа; type/kind/change_id в YAML не добавляются. Номера документов состоят из шести цифр и находятся в диапазоне 000001–999999. Номера существующих рабочих и архивных документов не переиспользуются. Удалённый неначатый change не резервирует номер; CLI не исследует Git. created и updated — строковые даты в кавычках, updated не раньше created.

Intent/Spec/Plan/SRS/ADR используют status draft/approved/superseded/cancelled; Research — draft/completed/superseded/cancelled. Journal не имеет status или execution. Execution находится только в Plan: not_started/in_progress/blocked/completed/cancelled.

Origin обозначает происхождение; research/adr — непосредственное влияние. Эти поля и supersedes добавляются по необходимости непустыми массивами строк через дефисы. Пустые поля опускаются. Research/adr указывают целый документ соответствующего типа. Supersedes поддерживается в Intent/SRS/Research/ADR и указывает заменяемый документ того же типа. Scope — непустой массив путей только в Spec.

Scope упорядочивают как дерево проекта: на каждом уровне сначала директории с их содержимым, затем файлы; имена сравнивают по алфавиту без учёта регистра. При совпадении имён без учёта регистра порядок определяется исходным написанием. Путь к отдельному файлу внутри директории относится к её ветке: например, `instructions/workflow.md`, затем `tests/**`, затем `AGENTS.md` и `README.md`. Порядок определяется по компонентам пути, без проверки существования файлов.

Origin указывают, когда содержание документа выведено из конкретного документа-источника. Последовательность задач, общий проект, ссылка на прежние результаты или необходимость завершить предыдущую задачу сами по себе не являются основанием для origin. Если содержательное происхождение не установлено, поле опускают.

| Отношение  | Источник → цель                                                  |
| ---------- | ---------------------------------------------------------------- |
| Covers     | AC → R задачной Spec или SRS                                     |
| Covers     | S → AC или R; S SRS → R SRS                                      |
| Covers     | P → AC, R, S или DOD                                             |
| Depends on | P → P                                                            |
| Changes    | R задачной Spec → R SRS                                          |
| Verifies   | V → фактически проверенные AC, R, S, DOD или ADR                 |
| supersedes | Новый Intent/SRS/Research/ADR → заменяемый документ того же типа |

Самоссылки запрещены; зависимости и замены не должны образовывать циклы. Обратные ссылки производны от прямых; текущий CLI их не выводит. Covers не доказывает успешную проверку; Verifies перечисляет только фактически проверенные цели. Changes не заменяет принятия изменённого обязательства. Правило plan-requirement-coverage в strict (и при явном включении в lite) принимает P → R и P → AC → R в пределах рабочего change, если каждая связь указана в Covers. Полную матрицу текущий validate не контролирует; эти правила соблюдает исполнитель по [общим инструкциям](../instructions/workflow.md).

## Актуальная форма и архив

Архив расположен в archive/changes, archive/specs, archive/adr и archive/research внутри documents_root. Расположение определяет архивность; ID остаётся глобально уникальным. Обычное обнаружение исключает архив, CLI индексирует его для адресов и занятых номеров. Конечные состояния и процедура переноса определены в [инструкции синхронизации и архивирования](../instructions/sync-and-archive.md).

Неархивные документы сравниваются с актуальной формой: несоответствия дают предупреждения без перезаписи. Архив не проверяется на полноту текущей формы. Ошибки чтения, YAML, идентичности, расположения, конечного состояния и текущих ссылок остаются ошибками целостности. Формальные проверки не подтверждают согласование, смысловую полноту или правильность поведения.

### Диагностики и исторические адресаты

CLI считает ссылки архивного документа и change с execution completed/cancelled историческими; остальные — текущими. Для ссылки Changes корректной дельты add отсутствие будущей цели разрешено. Историческая ссылка на R SRS проверяется как идентичность: сохранённый Before завершённой операции remove позволяет найти отменённое обязательство. Отменённый change такой опорой не служит. W_HISTORY сообщает об отсутствии опоры либо о том, что найденная идентичность не доказывает редакцию на момент события. Текст прежней редакции CLI не подставляет; агент сверяет дельту и Git. Потеря целого адресуемого документа остаётся ошибкой, кроме ссылки на исторический R SRS с явно сообщённым ограничением.

W_ARCHIVE_REFERENCE указывает источник, адресат и назначение текущей зависимости от архива; origin и supersedes исключены. W_SYNC_PENDING сообщает о неархивном completed-change с распознанной дельтой. W_FORM обозначает несоответствие формы: разделы, метаданные, объявления или состав полей дельты. Повреждённые адреса и дубликаты остаются ошибками. Проверка полноты и смысла Before/After, непереиспользования отменённых локальных ID и основания выбытия Research остаётся обязанностью агента; CLI проверяет форму и конечное состояние, но не доказывает эти факты.
