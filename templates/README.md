# Как использовать шаблоны

Пакет поставляет семь библиотечных форм. Готовые документы принадлежат проекту; обновление пакета меняет формы для новых документов и не перезаписывает существующие.

| Документ | Форма                      | Когда создаётся                                          |
| -------- | -------------------------- | -------------------------------------------------------- |
| Intent   | [intent.md](intent.md)     | Вместе со Spec и Plan командой new                       |
| Spec     | [spec.md](spec.md)         | Вместе с Intent и Plan командой new                      |
| Plan     | [plan.md](plan.md)         | Вместе с Intent и Spec командой new                      |
| Journal  | [journal.md](journal.md)   | Агентом с началом Implement                              |
| SRS      | [srs.md](srs.md)           | Агентом при необходимости устойчивых требований продукта |
| Research | [research.md](research.md) | Агентом для исследования открытого вопроса               |
| ADR      | [adr.md](adr.md)           | Агентом для существенного долговременного решения        |

New создаёт ровно три документа: Intent, Spec и Plan. Наличие остальных шаблонов не требует создавать пустые артефакты и не добавляет команд CLI.

## Заполнение и optional-блоки

Команда `new` подставляет в три формы `{{change_id}}`, `{{date}}`, `{{title}}`. Остальные формы заполняет агент: для Journal использует ID текущего change, для SRS/Research/ADR заменяет `{{document_id}}` полным свободным ID соответствующего типа; дату и заголовок также заполняет фактическими значениями. Это подсказки формы, не дополнительные параметры new.

Необязательные YAML-поля закомментированы строками `# optional:` и `#`; примеры адресов не становятся активными ссылками. Необязательные разделы Markdown отмечены стандартными HTML-комментариями `<!-- optional: … -->`. Агент заполняет применимые части, удаляет неприменимые вместе с подсказкой и исправляет связанные ссылки. После удаления R или шага удалите либо обновите обращения к нему. Комментарии «Заполнение» поясняют содержание блоков: после заполнения удалите их, сохранив сам раздел. Комментарий optional разрешает убрать неприменимый блок; обычная подсказка такого разрешения не даёт.

Маркер optional не исключает следующее активное содержимое из проверки и не отменяет применимые требования профиля. Strict требует явных требований и связей. Оставшийся `TODO(VF)` даёт ошибку validate; форма не подтверждает ни требования, ни согласование, ни успешную проверку. В готовых документах допустимы только существующие адресаты.

## Назначение разделов

Intent хранит цель, ограничения, контекст и AC с наблюдаемыми условиями и Verification. Examples перед Acceptance Criteria нужен только для уточнения результата. AC может покрывать требование задачной Spec или SRS; копировать AC в Spec не нужно.

Spec задаёт границы и проверяемые обязательства: поведение, форматы, ошибки, совместимость и инварианты. Scope добавляется для путей вне четырёх собственных артефактов. Предпочитайте узкие директории функциональной области; отдельные файлы указывайте для общих компонентов. Чтение смежного контекста не ограничено scope; необходимый рефакторинг допустим внутри принятого контракта и разрешённых путей. Выход за них согласуется до изменений. Protected_paths сохраняет запрет независимо от scope. Scenarios и дополнительные DOD нужны по смыслу; Given/When/Then — допустимая, но необязательная форма сценария. Неприменимый DOD не создаётся.

Plan содержит единственный checklist. Technical Approach нужен, если технические решения не раскрыты в шагах. Одной sequential-волны достаточно для простой задачи; дополнительные волны и parallel используются по необходимости. Волны идут последовательно. Depends on задаёт явную зависимость шага, не дублируя очевидный порядок. Отметка выполнения требует результата и применимых проверок. В Verification шага указываются недостающие практические детали выполнения проверки: тест, команда, фикстура, измерение, среда или ручная процедура. Если способ проверки уже достаточно конкретно описан в Intent или Spec, Plan ссылается на него.

Порядок тестирования задаётся в Plan независимо от lite/strict. Исправление дефекта начинается с воспроизводящего регрессионного теста; невозможность воспроизведения и альтернативная проверка фиксируются явно. TDD применяется, если выбран для задачи, и требует теста до соответствующей реализации.

Journal хранит точку продолжения, краткое основание согласования, существенные для текущего результата решения и фактические проверки. Полные копии других артефактов не требуются. V-блок появляется после реальной проверки, без заранее заполненного passed. В согласованном формате конечного состояния достаточно актуальных результатов с указанием входов и ограничений; хронология правок не требуется. Временные логи и манифесты не заменяют необходимый результат в Journal. Не указывайте абсолютные пути машины, временные установки и соседние проекты. Используйте команды от корня проекта, версии и идентификаторы проверенных входов. Различайте выполненный запуск, чужой отчёт и анализ кода. Итог должен учитывать последние разрешения и фактические повторы проверок.

SRS размещается в specs внутри documents_root; обязательны Purpose and Boundaries, Requirements и минимум одно R. Сценарии S добавляются по необходимости. Для одной ограниченной задачи отдельный SRS не обязателен.

Research размещается в research, ADR — в adr внутри documents_root. Стандартные названия и уровни разделов сохраняются. Текущий CLI проверяет метаданные и H1 этих документов, но не их H2/H3, полноту исследования или принятие решения. Ограничение CLI не отменяет обязательных разделов и правил заполнения.

Research обязательно содержит Research Question, Context and Scope, Method and Sources, Findings и Conclusion. Options and Trade-offs нужен при сравнении вариантов; Limitations and Open Questions — при существенных ограничениях или нерешённых вопросах; References — если нужен отдельный список источников. Существенные оговорки сохраняются независимо от наличия отдельного раздела. Method and Sources описывает метод и выбор источников, Findings связывает результаты с конкретными основаниями, References содержит библиографию. Источники доказательств не смешиваются с origin. Отрицательный результат и недостаток данных допустимы; completed означает завершение исследования, а не принятие рекомендации.

ADR обязательно содержит Context and Problem Statement и Decision Outcome, а внутри Decision Outcome — подразделы Consequences и Confirmation. В Consequences описываются существенные последствия. Confirmation задаёт постоянный способ проверки соблюдения решения; детали выполнения находятся в Plan, фактические результаты — в Journal. Considered Options нужен при рассмотренных альтернативах; искусственный второй вариант не добавляется. В Consequences сохраняются существенные последствия: положительный, отрицательный пункт и риск не обязаны присутствовать одновременно. Approved означает принятие решения, а не его реализацию.

Одна форма ADR содержит краткий вариант и расширения MADR. Для краткого варианта удалите необязательные Decision Drivers, Pros and Cons of the Options и More Information; Considered Options оставьте по применимости. Расширенный вариант раскрывает критерии выбора, аргументы по вариантам и дополнительные сведения. Все условные разделы и пункты отмечены optional; неприменимые блоки удаляются вместе с подсказками. При пересмотре принятого решения согласуются изменения к нему.

## Метаданные и отношения

ID определяет тип документа; type/kind/change_id в YAML не добавляются. Номера документов состоят из шести цифр и находятся в диапазоне 000001–999999. Номера не переиспользуются. created и updated — строковые даты в кавычках, updated не раньше created.

Intent/Spec/Plan/SRS/ADR используют status draft/approved/superseded/cancelled; Research — draft/completed/superseded/cancelled. Journal не имеет status или execution. Execution находится только в Plan: not_started/in_progress/blocked/completed/cancelled.

Origin обозначает происхождение; research/adr — непосредственное влияние. Эти поля и supersedes добавляются по необходимости непустыми массивами строк через дефисы. Пустые поля опускаются. Research/adr указывают целый документ соответствующего типа. Supersedes поддерживается в Intent/Research/ADR и указывает заменяемый документ того же типа. Scope — непустой массив путей только в Spec.

| Отношение  | Источник → цель                                              |
| ---------- | ------------------------------------------------------------ |
| Covers     | AC → R задачной Spec или SRS                                 |
| Covers     | S → AC или R; S SRS → R SRS                                  |
| Covers     | P → AC, R, S или DOD                                         |
| Depends on | P → P                                                        |
| Changes    | R задачной Spec → R SRS                                      |
| Verifies   | V → фактически проверенные AC, R, S, DOD или ADR             |
| supersedes | Новый Intent/Research/ADR → заменяемый документ того же типа |

Самоссылки запрещены; зависимости и замены не должны образовывать циклы. Обратные ссылки производны от прямых; текущий CLI их не выводит. Covers не доказывает успешную проверку; Verifies перечисляет только фактически проверенные цели. Changes не заменяет принятия изменённого обязательства. Полную матрицу текущий validate не контролирует; эти правила соблюдает исполнитель по [общим инструкциям](../instructions/workflow.md).
