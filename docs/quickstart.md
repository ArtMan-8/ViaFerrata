# Первое подключение ViaFerrata

ViaFerrata поставляет CLI, инструкции агенту и шаблоны. Человек задаёт цель и принимает существенные решения; агент готовит документы, вызывает CLI и проверяет изменение. CLI не вызывает модель и не заменяет среду агента.

## Среда и способ запуска

Нужны Node.js 24.x и npm. Пользовательский сценарий проверен на Linux x86_64; поддержка других ОС пока не подтверждена.

Выберите один из двух равноправных способов:

| Способ        | Установка и проверка                                     | Следующие вызовы                  |
| ------------- | -------------------------------------------------------- | --------------------------------- |
| Npx           | `npx viaferrata@latest --version`                        | `npx viaferrata@latest <команда>` |
| Глобальный vf | `npm install -g viaferrata@latest`, затем `vf --version` | `vf <команда>`                    |

Сообщите агенту выбранный способ запуска. Если проект закрепил версию, подставьте её вместо `latest`. Примеры далее используют npx; при глобальной установке заменяйте `npx viaferrata@latest` на `vf`.

## Подключение проекта

Целевой каталог должен существовать. Сначала получите пути к инструкциям из текущей установки, затем подключите проект:

```sh
npx viaferrata@latest --help
npx viaferrata@latest init /path/to/project --profile lite
cd /path/to/project
```

**Первое подключение.** Команда `vf init` создаёт `viaferrata.toml`, добавляет блок навигации в `AGENTS.md` и правило для временного каталога в `.gitignore`. Пользовательские данные сохраняются. Без аргумента `path` используется текущий каталог. При первом подключении явно выберите профиль `lite` или `strict`. Первое подключение внутри уже подключённого проекта запрещено.

По умолчанию документы создаются в `viaferrata/` внутри проекта. Чтобы выбрать другой каталог, при первом подключении выполните, например, `vf init --profile lite --documents-root docs/process` выбранным способом запуска. Команда запишет путь в TOML и покажет корень документов и результат для каждого файла подключения. Каталог появится, когда вы создадите первый комплект или самостоятельный документ командой `vf new`. Профиль `lite` включает базовые проверки, `strict` дополнительно проверяет покрытие требований шагами Plan и критериев приёмки записями Journal в deep-задачах.

Правило `/.viaferrata/` действует на неотслеживаемые файлы. Команда сохраняет индекс Git. Если временные файлы уже отслеживаются, решение об их удалении из индекса принимает владелец проекта.

Перед первой задачей сохраните подключение и настройки проекта отдельным коммитом Git. Базовый коммит первой deep-задачи должен содержать `viaferrata.toml` с выбранным профилем и обязательными правилами.

Вызовы и результаты команд описаны в [SRS «CLI-инструменты»](../viaferrata/specs/srs-000003-cli-tools.md). Если в диагностике указан ID правила, по нему можно найти строку в [каталоге встроенных правил](../viaferrata/specs/srs-000001-built-in-checks.md#system-overview).

Профиль `strict` не означает, что весь предусмотренный контроль реализован. Текущие ограничения перечислены в [README](../README.md#ограничения).

## От цели до проверки

Откройте подключённый проект в среде агента. Сообщите цель, ожидаемый результат и способ запуска ViaFerrata. Например: «Делаю трекер учебных курсов. Хочу добавить курс по названию и увидеть его в списке». Агент читает локальный `AGENTS.md`, находит `workflow.md` через `--help` и выбирает инструкции для задачи.

Для deep-задачи агент создаёт черновики:

```sh
npx viaferrata@latest new change "Название изменения"
npx viaferrata@latest validate
```

Команда `vf new change` создаёт Intent, Spec и Plan в `changes/change-NNNNNN/` внутри `documents_root`. Пока в черновиках есть активные маркеры `TODO(VF)`, команда `vf validate` сообщает `E_DRAFT_PLACEHOLDER` и возвращает код 1. Агент заполнит документы по [руководству шаблонов](../templates/README.md) и предложит согласовать цель, требования и план. Для простой vibe-задачи отдельный комплект не требуется.

Для отдельного документа выберите тип по цели. Например, `vf new srs "Политика хранения"` создаёт черновик требований в `specs/srs-NNNNNN.md` внутри корня документов. Вызов `vf new adr "Выбор хранилища"` создаёт запись решения в `adr/`, а `vf new research "Срок хранения"` — исследование в `research/`. При успехе CLI выводит ID и путь. Передайте их агенту для заполнения формы.

Команды `vf new` и `vf validate` ищут ближайший `viaferrata.toml` вверх от текущего каталога. Поэтому их можно вызывать из подкаталога проекта. Ошибочная ближайшая конфигурация останавливает поиск; CLI не выбирает другую конфигурацию ради успешного результата. Параметра `--root` нет.

При обновлении проекта со старыми дельтами проверьте рабочие и архивные Spec по [правилам перехода](../templates/README.md#дельта-требований).

## Проверка области изменений

Проверьте через `vf --help`, что установленная версия поддерживает `scope`. Ниже приведён пример для рабочего комплекта `change-000001`.

1. При согласовании выполните `vf scope change-000001 --digest`. Команда выводит сумму масок из Spec и работает до создания Journal.
2. При начале исполнения запишите в Journal решение пользователя, полный SHA исходного коммита и полученную сумму по [правилам Journal](../instructions/journal.md#согласование-и-решения).
3. При возобновлении работы и перед завершением задачи выполните `vf scope change-000001`.

Проверяются разность базы и HEAD, индекс, рабочее дерево и неигнорируемые untracked-файлы. При переносе учитываются оба пути. Команда сообщает слой и путь нарушения. При расхождении суммы сверьте Spec с решением пользователя. Вложенный корень проекта, изменённый симлинк, подмодуль или конфликт индекса требуют отдельного разбора.

## Завершение deep-задачи

Проверьте через `vf --help`, что установленная версия поддерживает `complete`. Закройте выполненные шаги Plan и запишите результаты в Journal. Проверьте комплект по правилам проекта, учтите замечания и повторите затронутые проверки. После успешного `vf scope change-NNNNNN` выполните `vf complete change-NNNNNN` в рабочем комплекте. При отказе команда укажет условие допуска. Если у задачи есть дельта SRS, после успешного перехода примените её и сразу архивируйте комплект по [правилам синхронизации](../instructions/sync-and-archive.md).

## Повтор init и конфликты

Повторите подключение без выбора нового профиля:

```sh
npx viaferrata@latest init /path/to/project
```

**Повторное подключение.** Команда `vf init` сохраняет существующий TOML побайтно и дополняет недостающие файлы подключения. Без флагов команда использует сохранённые профиль и корень документов. Можно повторить первоначальный вызов с тем же корнем. **Конфликт корня.** При несовпадении `vf init` сообщает о конфликте до записи. Проверьте `documents_root` в TOML и повторите вызов с этим корнем либо без флага.

Готовые файлы сохраняются без изменения байтов и времени модификации. Прежние штатные формы блока ViaFerrata в `AGENTS.md` также принимаются без переписывания. Если внутри блока есть ручная содержательная правка, `vf init` сообщает конфликт. Сохраните дополнения вне блока и разрешите различие перед повтором; автоматической перезаписи через force нет.

При сбое записи исправьте указанную причину и повторите `vf init`. Уже подготовленные части сохраняются; сообщение сообщает о выполненных изменениях. При ошибках использования или доступа CLI возвращает код 2.

## Продолжение в новой сессии

Передайте агенту каталог проекта, задачу и выбранный способ запуска: npx или глобальный vf. Агент повторяет `vf --help` этим способом, открывает актуальные пути инструкций и обнаруживает комплект по [общим правилам](../instructions/workflow.md#обнаружение-задачи).
