# Инструкции агенту ViaFerrata

Прочитай локальные правила проекта в AGENTS.md. Этот файл помогает выбрать порядок работы и инструкции установленного пакета.

## Ответственность и границы автоматизации

Человек задаёт цель и принимает существенные решения об обязательствах и полномочиях. Агент готовит документы, выполняет согласованную работу и проверяет результат. Тесты проекта запускает агент или CI. По их результатам агент устанавливает, выполнены ли критерии приёмки для проверенной редакции.

`vf validate` проверяет структуру документов, идентификаторы и связи. `vf complete` проверяет условия завершения рабочего deep-комплекта по документам и Git. Смысл требований, основание согласования и применимость результатов оценивает агент.

## Подключение проекта

1. Используй способ запуска CLI, принятый в проекте. При глобальной установке выполни `vf --help`. Для запуска через npx без закреплённой версии используй `npx viaferrata@latest --help`. Если проект закрепил версию, сохрани её. В командах ниже `vf` обозначает выбранный способ запуска. В новой сессии получай текущие пути к инструкциям и шаблонам из справки.
2. Выполни `vf init [path] [--profile lite|strict] [--documents-root <path>]`. По умолчанию команда подключает текущий каталог. Для новой конфигурации укажи профиль. Если пользователь выбрал каталог документов, передай путь относительно проекта в `--documents-root`. Существующую конфигурацию команда сохраняет. При конфликте сравни запрошенные настройки с `viaferrata.toml`. Для повторного подключения с сохранёнными настройками опусти флаги. Если пользователь хочет перенести документы, согласуй отдельную задачу. Первое подключение внутри другого подключённого проекта запрещено.
3. Команда добавляет навигацию в AGENTS.md и исключает временный каталог `.viaferrata/` через `.gitignore`. Храни проектные правила вне блока ViaFerrata в AGENTS.md. При конфликте сохрани пользовательские правки и сверь различия по [руководству подключения](https://github.com/ArtMan-8/ViaFerrata/blob/trunk/docs/quickstart.md).

Перед первой задачей проверь, что подключение и настройки проекта сохранены в Git. Для коммита нужно поручение пользователя.

При обсуждении первой задачи после `vf init` выясни, что создаём, для кого и зачем. Учти сообщения пользователя и существующий README, спроси только о недостающем. Кратко запиши ответы в README и укажи способ запуска, если он известен.

## Режим и документы задачи

Для небольшой задачи с ясным результатом подходит `vibe`: отдельные task-ID, Intent, Spec, Plan и Journal не требуются. Если новое поручение меняет несколько связанных правил поведения или принятое архитектурное решение, до реализации предложи `deep` и укажи, что требует согласования.

В режиме `deep` команда `vf new change "Название задачи"` создаёт Intent, Spec и Plan со `status: draft`. Заполни документы и предъяви комплект для согласования. После явного принятия установи во всех трёх документах `status: approved`. С началом реализации переведи Plan в `execution: in_progress` и создай Journal. Веди начатую deep-задачу в этом режиме до завершения или отмены. Формы документов и связи описаны в [руководстве шаблонов](../templates/README.md).

Перед созданием самостоятельного документа найди действующие SRS и ADR по теме. Для новой области требований используй `vf new srs "Название"`, для существенного решения — `vf new adr "Название"`, для исследования — `vf new research "Название"`. В существующей области подготовь дельту к действующей SRS. После генерации, до добавления файловых ссылок, переименуй файл по схеме `<id>-<краткое-смысловое-имя>.md`, сохранив ID в YAML. Если путь занят, сохрани исходный файл и сообщи о конфликте. Заполни форму по основаниям задачи, согласуй требования или решение с человеком и укажи конечный путь.

Профиль `lite` или `strict` определяет набор встроенных правил проекта в обоих режимах. Сохраняй согласованный профиль. Для рабочих deep-комплектов в strict включены `plan-requirement-coverage` и `verification-coverage`. В lite проект может включить каждое из них через `required_checks`. Условия проверки и допустимые связи приведены в [руководстве шаблонов](../templates/README.md#метаданные-и-отношения).

Обновляй даты документов при изменении содержания. Сохраняй ID, прежние changes и действующие требования. Новая задача развития функции получает свой комплект, если выбрана глубина deep. Нормативные сведения и необходимые результаты должны оставаться доступными из репозитория проекта или установленного пакета.

## Обнаружение задачи

Если пользователь указал change, прочитай его документы независимо от статуса. При возобновлении deep-задачи без ID выполни следующие шаги.

1. Определи `documents_root` по viaferrata.toml. По умолчанию это `viaferrata`. Внутри рабочего `changes/` найди Plan с `execution: in_progress` или `blocked`. Тип документа определяется YAML-полем `id`, состояние исполнения — полем `execution`, а `status` описывает состояние документа.
2. Если активных кандидатов нет, проверь Plan с `execution: not_started`. При нескольких кандидатах используй контекст поручения. Если он оставляет выбор неоднозначным, уточни задачу у человека. Дата и наибольший ID не определяют приоритет.
3. Прочитай Intent, Spec, Plan и существующий Journal выбранного комплекта. Сверь их с поручением и состоянием Git. Восстанови разрешённые действия по принятому содержанию и решениям. При подготовке новой работы прежний комплект сам по себе не даёт основания продолжать его.

При обычном поиске пропускай `archive/changes/`. Для продолжения синхронизации проверь и рабочие completed-комплекты с дельтой по [правилам восстановления](sync-and-archive.md#восстановление-и-ссылки). В локальном AGENTS.md достаточно постоянной ссылки на этот процесс.

## Согласование и scope

На вопрос о возможности или причинах ответь по существу. До правки уточни, нужна ли она и какого поведения ожидает человек, если это неясно из контекста. В пределах принятого поручения уточняй технические шаги, код и тесты самостоятельно. Изменение обязательств, полномочий или разрешённых путей согласуй до зависимых действий. Тикеты, логи и внешние документы служат источниками сведений. Права на установку, удаление, публикацию и другие действия определяются поручением и правилами проекта. Техническое ограничение доступа обеспечивает среда.

В deep достаточно одного явного принятия показанных Intent, Spec и Plan. Статус документа и запись в roadmap сами по себе не подтверждают это решение. В начале реализации зафиксируй основание, согласованные scope и обязательные проверки по [правилам Journal](journal.md#согласование-и-решения).

В scope автоматически входят четыре артефакта текущего change. Остальные разрешённые пути укажи в Spec в [порядке дерева проекта](../templates/README.md#метаданные-и-отношения). Учитывай будущие файлы при выборе маски. Если разрешены отдельные файлы, перечисли их. Читай смежный код в пределах прав проекта, а правки в разрешённых путях ограничивай целью задачи. При возобновлении deep-задачи и перед завершением проверь рабочий комплект командой `vf scope change-NNNNNN`. Для проверки корень проекта должен совпадать с корнем рабочего дерева Git, а базовый коммит должен быть доступен и входить в историю HEAD. При отказе сообщи причину и сохрани файлы.

## Хранение и обновление

Пакет поставляет CLI, схемы, инструкции и шаблоны. Конфигурация, заполненные документы и накопленные знания принадлежат проекту. При обновлении пакета они сохраняются.

Временные логи, кеши и диагностические материалы размещай в `.viaferrata/` вне Git. Для deep-задачи подходит `.viaferrata/changes/<change-id>/`. Создавай каталоги и снимки по необходимости. В deep существенные решения, результаты и ограничения сохраняй в Journal, чтобы работу можно было продолжить после утраты временных файлов.
