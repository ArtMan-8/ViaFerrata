# Ведение Journal

Читай перед созданием, обновлением или проверкой Journal, включая возобновление deep-задачи. Применяй вместе с [обязательными правилами](workflow.md) и [руководством шаблонов](../templates/README.md).

Journal должен быть самодостаточным. Не копируй в него требования и checklist.

## Согласование и решения

При начале исполнения укажи в Significant Events, какой комплект пользователь принял и на каких условиях. Сохрани доступное основание решения, его источник, известные время и участника. Короткий ответ вроде «да» свяжи с конкретным предложением. Укажи, если основание записано агентом по переписке или известно из пересказа.

Принятую дельту запиши сразу, до зависимых действий. Назови изменённые обязательства или полномочия. Воспроизведи точный путь, значение или исключение, если от него зависит разрешение. При частичном принятии укажи, какие прежние условия продолжают действовать. Например, если пользователь разрешил добавить файл в scope и сохранил обязательную проверку, запиши путь и название этой проверки.

Если принятая редакция сохранена в Git, укажи её ревизию. Иначе обозначь предел восстановления: ссылка на изменяемый файл или один хеш не сохраняют исторический текст. Полные копии Intent/Spec/Plan не требуются. Итоговый коммит нельзя выдавать за редакцию, принятую до реализации.

В новом Journal запиши каждое решение для сводки строкой в список `decisions` внутри YAML-блока Significant Events. Сохрани в строке принятое содержание и основание. Ручные пояснения можно оставить рядом.

При согласовании deep-задачи установи полный SHA исходного коммита Git. Если задача начинается с текущего коммита, получи его через `git rev-parse HEAD`. Выполни `vf scope change-NNNNNN --digest` для согласованной Spec. В Significant Events запиши в YAML значение `scope_check.base` и полученную сумму `scope_check.digest` по форме Journal. Сохраняй базу до конца задачи. После принятой дельты сначала запиши точное изменение в decisions, затем обнови сумму. При расхождении суммы без принятого решения восстанови согласованную область.

При согласовании перечня обязательных проверок добавь в Significant Events `completion_digest`. Вычисли SHA-256 от UTF-8 представления `JSON.stringify(checks.toSorted())`, где checks — согласованный массив строк completion_checks из Definition of Done Spec. При согласованной дельте запиши её основание и обнови сумму. Сохраняй исходный профиль проекта и включённые обязательные правила.

## Синхронизация и перенос

Синхронизация и архивирование завершённого change не добавляют записи в Journal. Решение о судьбе частично исполненной отменённой задачи сохраняется до переноса. Для удаляемого неначатого change Journal не создаётся. Не дублируй процедуру из [инструкции синхронизации и архивирования](sync-and-archive.md).

## Проверки и результаты

В новом Journal веди один YAML-блок с ключом `checks` в Verification. До первого прогона оставь `checks: []`. После прогона заполни запись по примеру в [шаблоне Journal](../templates/journal.md#verification).

Для неизвестной редакции используй `revision: null`. При известном исполнителе можно добавить строку `executor`. В Verifies перечисляй фактически проверенные цели. В Revision той же записи V указывай редакцию, общую для этих целей. Без неё редакция неизвестна, даже если сводка checks содержит passed и редакцию другой проверки. Команду, среду и ограничения можно описать рядом с блоком. Сводку читают через `vf summary change-NNNNNN`; в vibe передают отчёт с теми же списками через `vf summary --stdin`. Основание согласования передают в необязательном списке `decisions`.

Для выполненных проверок указывай команды относительно корня проекта, версии инструментов, идентифицируемые входы, результаты и ограничения. Различай собственный запуск, чужой отчёт и вывод из чтения кода. Запланированный повтор остаётся в Plan или точке продолжения; в Verification результат появляется только после выполнения.

Не включай абсолютные пути машины, пути временных установок и ссылки на соседние проекты или каталоги. Не ссылайся на локальные логи, снимки и другие недоступные читателю данные, включая файлы внутри `.viaferrata/`: необходимые результаты и ограничения излагай в самом документе. Для установленного CLI укажи версию, способ установки и при необходимости идентификатор пакета; команды записывай через vf.

По согласованному формату конечного состояния можно убрать хронологию правок и неактуальные результаты. Сохрани основание согласования, влияющие на итог решения, текущие проверки и ограничения; не скрывай ошибку без подтверждённого успешного повтора.

## Отчёт для завершения

Для каждой обязательной проверки запиши один текущий subject, outcome, source и revision. При повторе укажи, что подтвердил новый запуск, и актуализируй итоговую запись. Для зачёта AC добавь в checks поле verification с локальным ID записи V. Заполни Verifies и Revision этой записи. В разделе Result опиши достигнутый результат и ограничения. После этого выполни vf complete change-NNNNNN.
