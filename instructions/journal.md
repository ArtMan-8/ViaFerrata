# Ведение Journal

С началом реализации deep-задачи создай `journal.md` в рабочем комплекте по [шаблону Journal](../templates/journal.md). В `Current State` укажи фактическое состояние и следующий шаг или препятствие. При передаче работы сверь запись с Plan и Git. Требования хранятся в Intent и Spec, checklist — в Plan.

## Согласование и решения

В начале реализации укажи в разделе `Significant Events`, какой комплект пользователь принял и на каких условиях. Сохрани доступное основание решения, его источник, известные время и участника. Короткий ответ вроде «да» свяжи с конкретным предложением. Укажи, если основание записано агентом по переписке или известно из пересказа.

Принятую дельту запиши сразу, до зависимых действий. Назови изменённые обязательства или полномочия. Воспроизведи точный путь, значение или исключение, если от него зависит разрешение. При частичном принятии укажи, какие прежние условия продолжают действовать. Например, если пользователь разрешил добавить файл в scope и сохранил обязательную проверку, запиши путь и название этой проверки.

Если принятая редакция сохранена в Git, укажи её ревизию. Иначе обозначь предел восстановления: ссылка на изменяемый файл или один хеш не сохраняют исторический текст. Полные копии Intent/Spec/Plan не требуются. Итоговый коммит нельзя выдавать за редакцию, принятую до реализации.

В новом Journal запиши каждое решение для сводки строкой в список `decisions` внутри YAML-блока Significant Events. Сохрани в строке принятое содержание и основание. Ручные пояснения можно оставить рядом.

Для `scope_check.base` укажи полный SHA исходного коммита, содержащего настройки проекта в `viaferrata.toml`. Если задача начинается с текущего коммита, получи SHA через `git rev-parse HEAD`. Для согласованной Spec выполни `vf scope change-NNNNNN --digest` и запиши результат в `scope_check.digest`. Оба поля находятся в YAML-блоке Significant Events. Сохраняй базу до конца задачи. После принятой дельты сначала запиши точное изменение в `decisions`, затем обнови сумму. При расхождении суммы без принятого решения восстанови согласованную область.

При согласовании перечня обязательных проверок добавь в Significant Events `completion_digest`. Вычисли SHA-256 по байтам UTF-8 строки `JSON.stringify(checks.toSorted())`, где `checks` — согласованный массив строк `completion_checks` из раздела `Definition of Done` в Spec. При согласованной дельте запиши её основание и обнови сумму. Сохраняй исходный профиль проекта и включённые обязательные правила.

## Синхронизация и перенос

Решение о результате частично выполненной отменённой задачи запиши до переноса. При удалении неначатого change отдельный Journal не требуется. Содержание завершённого Journal сохраняется при [синхронизации и архивировании](sync-and-archive.md).

## Проверки и результаты

В новом Journal веди один YAML-блок с ключом `checks` в Verification. До первого прогона оставь `checks: []`. После прогона заполни запись по примеру в [шаблоне Journal](../templates/journal.md#verification).

Для неизвестной редакции используй `revision: null`. При известном исполнителе можно добавить строку `executor`. Связь проверки с целями укажи в записи V по правилам ниже. Команду, среду и ограничения можно описать рядом с блоком.

`vf summary change-NNNNNN` выводит записи рабочего или архивного Journal. Код 0 означает, что CLI прочитал отчёт, в том числе когда в нём записан `failed`. В vibe для сводки можно передать один YAML- или JSON-отчёт через `vf summary --stdin`. В отчёте нужен список `checks`, список `decisions` необязателен.

Для выполненных проверок указывай команды относительно корня проекта, версии инструментов, идентифицируемые входы, результаты и ограничения. Различай собственный запуск, чужой отчёт и вывод из чтения кода. Запланированный повтор остаётся в Plan или точке продолжения; в Verification результат появляется только после выполнения.

Не включай абсолютные пути машины, пути временных установок и ссылки на соседние проекты или каталоги. Не ссылайся на локальные логи, снимки и другие недоступные читателю данные, включая файлы внутри `.viaferrata/`: необходимые результаты и ограничения излагай в самом документе. Для установленного CLI укажи версию, способ установки и при необходимости идентификатор пакета; команды записывай через vf.

По согласованному формату конечного состояния можно убрать хронологию правок и неактуальные результаты. Сохрани основание согласования, влияющие на итог решения, текущие проверки и ограничения; не скрывай ошибку без подтверждённого успешного повтора.

## Отчёт для завершения

Для каждого названия из `completion_checks` в Spec оставь в `checks` одну текущую запись с таким же `subject`. Для допуска нужны `outcome: passed`, источник в `source` и известная редакция в `revision`. При повторе обнови текущую запись и укажи, что подтвердил новый запуск.

В каждом V перечисли в `Verifies` фактически проверенные цели, в `Revision` укажи общую для них редакцию, в `Result` запиши наблюдаемый результат. Для зачёта AC укажи локальный ID этой записи V в поле `verification` соответствующей строки `checks`. Когда включено правило `verification-coverage`, для каждого AC нужна хотя бы одна такая успешная проверка с известной редакцией. Один V может подтвердить несколько AC.

В итоговом разделе `Result` опиши достигнутое поведение и ограничения. Затем следуй [порядку завершения deep-задачи](implementation.md#завершение-и-продолжение).
