# R-0001: Рантайм, платформы и доставка — сравнение Node.js, Bun и Deno

Все замеры выполнены в один день на одной машине; методика и стенд описаны ниже, чтобы числа можно было перепроверить. Факты из документации отмечены ссылкой и датой проверки в разделе `References`.

## Research question

Какой рантайм, набор платформ и канал доставки обоснованы для ViaFerrata при допущении, что Node.js у целевого пользователя уже есть, а скорость запуска не является главным драйвером?

Подвопросы:

1. На чём может работать ядро: Node.js, Bun или Deno; что дают стирание типов, тесты, проверка типов и сборка в каждом из них.
2. Какие API, на которые опирается проект, реально работают в каждом рантайме.
3. Как соотносятся способы доставки: npm-пакет, standalone-бинарник, skills/plugin-канал.
4. Какие ОС и версии Node поддерживаются с первого дня и как это проверяется, если среда разработки — WSL2.
5. Как технически устроены другие SDD-инструменты и является ли выбор Node.js + TypeScript + npm типичным.

## Context and scope

Вопрос возник на этапе выбора фундамента инструмента, до появления кода: от него зависят структура проекта, CI и способ доставки.

Принятые продуктовые допущения:

- целевой пользователь — разработчик, у которого Node.js уже есть; если его нет, пользователь устанавливает Node. Это принятый риск, а не задача, которую обязан решить бинарник;
- простота цепочки поставки важнее скорости запуска и скорости тестов;
- один артефакт для поддерживаемых ОС и архитектур предпочтительнее набора платформенных сборок;
- при нарушении жёсткого требования Node или появлении продуктового требования «работать без Node» решение пересматривается отдельно.

В границах: Node.js 24.22.2 как продуктовый минимум, актуальная LTS Node для CI, Bun 1.4.4 и Deno 2.9.6; способы доставки npm, standalone-бинарники и skills/plugin-канал; Linux, macOS и Windows.

Вне границ: переписывание на Go, Rust или другом языке; другие JS-рантаймы (LLRT, QuickJS, Hermes, workerd); выбор линтера и форматтера; способ сборки релизного артефакта; порядок выпуска версий 0.x. Эти вопросы решаются отдельно.

## Method and sources

- **Стенд:** WSL2, Ubuntu 24.04.5 LTS, x86-64, 12 ядер, 31 ГБ; ядро 6.18.54.1-microsoft-standard-WSL2.
- **Node:** 24.22.2 из nvm, npm 11.19.1; `process.features.typescript` — `strip`; amaro 1.1.11.
- **Bun:** 1.4.4.
- **Deno:** 2.9.6 (stable, x86_64-unknown-linux-gnu), V8 15.0.245.2, встроенный TypeScript 6.0.3.
- **TypeScript:** 5.9.3 и 7.0.2; `@types/node` 26.4.0.
- **Фикстура:** 40 TS-модулей и вход `cli.ts`, 3 173 строки, дерево относительных импортов с расширениями `.ts`; 20 тестовых файлов по 5 тестов, всего 100 тестов на `node:test`/`node:assert`. В основном коде нет Node-специфичных API, кроме `console.log`; форма и размер — прикидка будущего ядра инструмента, а не настоящий код.
- **Замеры запуска:** 20 прогонов на сценарий, медиана и разброс; время — настенные часы родительского процесса вокруг `spawnSync` с `shell: false`, то есть включает запуск рантайма; перед серией — прогрев.
- **Тесты:** 5 прогонов на сценарий. **Проверка типов и сборка:** 5 прогонов, кроме отдельных случаев, указанных в таблицах.
- **Проверка API:** отдельные маленькие программы для `node:sqlite` с FTS5, `util.parseArgs`, `node:test`, `node:crypto`, `module.stripTypeScriptTypes`, `process.features.typescript`, `import.meta.url`.
- **Бинарники:** `bun build --compile`, `deno compile`, Node SEA через `postject`; кросс-сборка для Windows и macOS проверялась только сборкой, без запуска.
- **Обзор SDD-инструментов:** чтение публичных репозиториев, манифестов, скриптов сборки и документации; версии и коммиты зафиксированы на 2026-11-01. Инструменты не устанавливались и не запускались, поэтому выводы об их рантайме и доставке сделаны по файлам сборки и документации.
- **Не проверено:** macOS и нативный Windows, Node 26 локально (в nvm только 24.22.2), реальный код ViaFerrata, npm provenance. Подробности — `Limitations`.

## Findings

### Архитектура и движки

- **Node.js** написан на C++ и использует V8; в замерах — V8 13.6.
- **Bun** написан на Zig и использует JavaScriptCore; в замерах — Bun 1.4.4.
- **Deno** написан на Rust и использует V8; в замерах — Deno 2.9.6, V8 15.0.245.2.

Сам по себе движок не решает выбор: важнее, какие API проекта работают и какую цену добавляет рантайм. Поэтому ниже — измерения и проверка совместимости, а не сравнение «V8 против JavaScriptCore».

### Старт

| Сценарий | Node 24.22.2 | Bun 1.4.4 | Deno 2.9.6 |
|---|---:|---:|---:|
| пустой запуск (`-e ""` / `eval ""`) | 36,9 (32,1–44,1) | 2,4 (2,1–3,1) | 23,3 (21,9–27,4) |
| `hello.ts`, одна строка | 84,2 (75,6–100,3) | 5,8 (5,4–8,7) | 19,8 (18,6–24,9) |
| `cli.ts`, 40 модулей TS | 127,0 (121,1–140,3) | 10,8 (10,4–13,4) | 23,7 (22,6–27,9) |
| собранный `dist/cli.js` | 54,7 (45,4–59,4) | 11,1 (10,4–12,4) | 22,9 (21,5–26,5) |
| `cli.ts`, тёплый `NODE_COMPILE_CACHE` | 53,3 (45,4–64,6) | — | — |
| `cli.ts`, холодный кеш (первый прогон) | 132,2 (123,2–143,7), n=5 | — | — |

Медиана, мс; в скобках — мин–макс, n=20, если не указано иное.

Что видно:

- Bun запускается в 5–15 раз быстрее Node на всех сценариях; Deno — между ними;
- на 40 модулях TypeScript как есть Node тратит 127 мс, собранный JS — 55 мс;
- тёплый кеш компиляции Node почти сравнивает TypeScript с собранным JS (53 против 55 мс), холодный первый прогон дороже;
- Bun тоже создаёт каталог `NODE_COMPILE_CACHE` (около 148 КиБ), но выигрыша на этой фикстуре не даёт: тёплый 12,1 мс против 11,6 мс без кеша, холодный — 23,7 мс.

Скорость — реальное преимущество Bun, но при принятом допущении она не является драйвером выбора. Для CLI, который запускается хуком на каждое действие, разница 11 против 127 мс заметна; для продукта, где Node уже есть и важнее предсказуемость, она не перевешивает остальные ограничения.

### Тесты

| Раннер | Медиана, мс (мин–макс) |
|---|---:|
| `node --test "test/*.test.ts"` | 653,3 (621,0–711,0) |
| `bun test` (Bun 1.4.4) | 64,3 (62,7–72,5) |
| `deno test --no-check test/` | 2 148,2 (2 066,9–2 175,5) |

Во всех случаях — 100 из 100 тестов. Bun исполняет файлы на `node:test` через свой раннер; прямой `bun <файл>` с `node:test` падает: `Cannot use test outside of the test runner. Run "bun test"`. Deno запускает те же тесты через `deno test`, но в этой конфигурации только с `--no-check`: без него не находится `npm:@types/node`. Это ограничение конфигурации фикстуры, а не приговор Deno.

Скорость тестов — преимущество разработки, а не продукта. При выборе рантайма она не перевешивает вторую runtime-предпосылку.

### Проверка типов и сборка

| Команда | Время | MaxRSS |
|---|---:|---:|
| `tsc` 7.0.2 `--noEmit` | 0,15–0,17 с | 54 112–54 820 КиБ |
| `tsc` 5.9.3 `--noEmit` | 1,52–1,71 с | 210 768–215 608 КиБ |
| `deno check src/cli.ts` | 0,62–0,64 с | 156 812–160 556 КиБ |

У Bun встроенной проверки типов нет: `bun build` и `bun run` транспилируют без проверки. На файле с ошибкой `const value: number = "not a number"` tsc 7, tsc 5.9 и `deno check` сообщают TS2322, а `bun build` и `bun run` успешно собирают и исполняют код. Поэтому при любом варианте с Bun `tsc` всё равно остаётся в цепочке.

| Сборка | Время | Размер | Файлов |
|---|---:|---:|---:|
| `tsc` 7.0.2 в `outDir` | 164,5 мс (160,9–213,6), n=5 | 88 907 Б | 41 |
| `tsc` 5.9.3 в `outDir` | 1 675,8 мс (1 636,0–1 677,9), n=3 | 88 907 Б | 41 |
| `bun build src/cli.ts --target=bun` | 9,6 мс (9,3–10,4) | 4 929 Б (bundle) | 1 |
| `bun build --compile --target=bun-linux-x64` 1.4.4 | 200,4 мс (187,5–292,5), n=5 | 109 127 856 Б (104,1 МиБ) | 1 |
| `deno compile` с проверкой типов | 1 505,2 мс (1 372,6–1 602,6), n=5 | 104 428 096 Б (99,6 МиБ) | 1 |
| `deno compile --no-check` | 815,8 мс (777,8–932,8), n=5 | 104 428 088 Б (99,6 МиБ) | 1 |

`bun build` включает 15 достижимых модулей из 41 (tree-shaking), `tsc` — все 41. `bun build --compile` — это копия рантайма с внедрённым бандлом, отсюда размер около размера рантайма. Сборка Bun быстрая, но проверку типов не заменяет.

### Синтаксис TypeScript

| Синтаксис | Node strip-only | Node `--experimental-transform-types` | Bun 1.4.4 | Deno 2.9.6 |
|---|---|---|---|---|
| `enum` | ошибка `ERR_UNSUPPORTED_TYPESCRIPT_SYNTAX` | работает | работает | работает |
| параметры-свойства конструктора | ошибка | работает | работает | работает |
| `namespace` с кодом | ошибка | работает | работает | работает |

В Node 24 стирание типов стабильно (Stability 2), предупреждений при запуске `.ts` нет; относительные импорты указываются с расширением `.ts`, типы импортируются через `import type`, `paths` из `tsconfig.json` не преобразуются. Проект уже ограничивает себя `erasableSyntaxOnly`, поэтому ограничение Node принято осознанно. Bun и Deno принимают больше синтаксиса, но это преимущество не используется: код всё равно должен запускаться в Node.

`module.stripTypeScriptTypes` есть в Node (статус Release candidate, печатает `ExperimentalWarning`) и в Deno; в Bun его нет — аналог `new Bun.Transpiler({ loader: "ts" }).transformSync()`. `process.features.typescript`: `strip` в Node, `transform` в Bun и Deno.

### Совместимость API

| API | Node 24.22.2 | Bun 1.4.4 | Deno 2.9.6 |
|---|---|---|---|
| `node:sqlite` с FTS5 | работает, SQLite 3.53.4 | работает, 3.53.4 | работает, 3.53.2 |
| `util.parseArgs` | работает | работает | работает |
| `node:test` | работает через `node --test` | только через `bun test` | через `deno test`; с проверкой типов нужен `@types/node` |
| `node:crypto` (sha256, randomUUID) | работает | работает | работает |
| `import.meta.url` + чтение ресурса | работает | работает | работает; `deno run` требует `--allow-read` |
| `module.stripTypeScriptTypes` | функция, experimental | нет | функция |

Критичные для проекта API работают во всех трёх рантаймах; заменять `node:sqlite` на `bun:sqlite` или `Deno.test` не требуется. Это важный результат: отказ от Bun/Deno — не техническая невозможность, а продуктовая цена.

### Упаковка и установка

Собран минимальный пакет `viaferrata@0.0.0` (`bin: {vf: "bin/vf.mjs"}`, `files: ["bin"]`, `type: module`, `engines.node >= 22.18.0`):

- `npm pack` дал тарбол 440 Б; внутри только `package.json` и `bin/vf.mjs`;
- `npm install --offline <тарбол>` в чистый каталог прошёл без сети;
- шим `node_modules/.bin/vf` запускается;
- прямой запуск `node .../bin/vf.mjs`, `bun .../bin/vf.mjs` и `deno run .../bin/vf.mjs` печатает ожидаемое.

Ранее проверялся более полный пакет с 41 файлом: тарбол 6,4 КБ, 168 КБ распакованного JS; вывод тот же — npm-установка и прямой запуск работают. Полный артефакт будет проверен в T-0001.

Node не запускает `.ts` внутри `node_modules` (`ERR_UNSUPPORTED_NODE_MODULES_TYPE_STRIPPING`), поэтому для npm нужен собранный JavaScript. Это не зависит от выбора Bun/Deno: пакет должен работать в Node.

Имя `viaferrata` в npm свободно; зарезервировать его пустышкой нельзя (Terms of Use). Первая публикация — вручную, с 2FA. Дальше — trusted publishing из GitHub Actions по OIDC: нужны npm CLI ≥ 11.5.1 и Node ≥ 22.14; у 24.22.2 в комплекте npm 11.19.1. Новая конфигурация trusted publisher должна опубликовать пакет в течение двух дней, иначе истекает; на пакет можно добавить до 10 издателей.

### Права и песочница

- **Deno:** есть `--allow-read`, `--allow-write`, `--allow-net`, `--allow-env`, `--allow-import`, `-A`. `deno run` без `--allow-read` падает с `NotCapable`; `--deny-read` даёт тот же отказ. `deno eval` в этом стенде читал файл без флага — особенность eval, не run.
- **Node:** модель `--permission` (Stability 2, стабильная с 23.5.0/22.13.0) — «seat belt», не полноценная песочница; без разрешений — `ERR_ACCESS_DENIED` / `FileSystemRead`, с `--allow-fs-read` работает.
- **Bun:** в 1.4.4 нет флагов разрешений и собственной песочницы; чтение файла без флагов работает.

Для ViaFerrata главная граница — песочница хоста (Claude Code и другие), а не рантайм CLI. Deno-права дают больше изоляции, но добавляют `--allow-*` в каждую команду хука; Node-модель стабильная, но «seat belt» и не заменяет хост; Bun в этом отношении не даёт ничего. Поэтому безопасность не перевешивает выбора Node, но и не является аргументом против него.

### Платформы и сроки поддержки

Node (документация, 2026-11-01):

- 24.22.2 — LTS «Krypton», страница релиза 2026-10-28 (в индексе `dist` — 2026-10-27); maintenance с 2026-10-20, конец поддержки 2028-04-30;
- 26.13.0 — LTS «Lithium», 2026-10-28, конец поддержки 2029-04-30;
- минимальные ОС для Node 24 (BUILDING.md): Linux — ядро ≥ 4.18 и glibc ≥ 2.28; Windows — ≥ 10/Server 2016; macOS — ≥ 13.5; сборки есть для linux x64/arm64, macOS x64/arm64, Windows x64/arm64;
- раннеры GitHub: `ubuntu-24.04` (x64), `macos-26` (arm64, это и есть `macos-latest`), `windows-2025` (x64); Intel-macOS — отдельные метки `macos-26-intel` и `macos-15-intel`; Windows arm64 раннеров нет.

Bun и Deno документально поддерживают Linux, macOS и Windows, но в этом исследовании их бинарники для Windows и macOS только собраны и не запускались. Для Node нативный Windows и macOS тоже не запускались локально; поддержка берётся из документации и проверяется матрицей CI (ADR-0003). Это риск для всех трёх вариантов, но у Node длинная история и уже запланированная матрица.

Хуки Claude Code (документация, 2026-11-01): exec-форма включается полем `args` — команда запускается без shell; на Windows exec-форма требует настоящий исполняемый файл, шимы `.cmd` и `.bat` из `node_modules/.bin` не запускаются; рабочий приём на всех ОС — `node` плюс путь к скрипту.

Что видно:

- **Node/npm — крупнейший единичный кластер**, но не большинство: четыре инструмента из десяти на Node/npm (OpenSpec, GSD Core, BMAD v6, `skills`); два на Python; три без своего рантайма (Superpowers, Conductor, Agent OS); BMAD V7 — тоже без рантайма; один проприетарный;
- **Bun использует только OpenSpec, и только в релизном CI** для `bun build --compile`; пользовательский рантайм OpenSpec — Node. **Deno не использует никто** из проверенных;
- **single binary — ниша:** OpenSpec добавляет его как escape hatch, Kiro — как единственный канал; больше никто;
- **Node + TypeScript + npm в чистом виде среди SDD — OpenSpec и GSD Core** (плюс `skills` CLI как близкий пример); BMAD v6 — Node + plain JS; Spec Kit и Spec Kitty — Python. TypeScript не является нормой среди всех десяти: его используют OpenSpec, GSD Core и `skills`, а BMAD v6 — plain JS;
- повторяющиеся паттерны: CLI-генератор артефактов хоста; Python-wheel с зашитыми шаблонами; npm как установщик, а не библиотека; git URL и skills/plugin-маркетплейсы; опциональный standalone-бинарник как escape hatch;
- своя модель разрешений/песочницы — только у Kiro; остальные делегируют хосту.

Вывод: выбор ViaFerrata **не однобокий**, но и не «так делают все». Node + TypeScript + npm — самый крупный кластер, а он объясняется нашими ограничениями: Node уже есть, npm даёт один канал, Windows/macOS поддерживаются, а скорость не является драйвером. Bun как продуктовый рантайм выделялся бы сильнее, чем Node.

## Options and trade-offs

Критерии: **B** — совместимость и предсказуемость на Linux, macOS и Windows, один артефакт, зрелые API; **E** — простота цепочки поставки; **Node предполагается**; скорость — не драйвер.

### Node.js 24 + TypeScript со стиранием типов + npm

- Хорошо: одна runtime-предпосылка; npm как единственный канал; ноль runtime-зависимостей; зрелые Windows/macOS; `node:sqlite` FTS5, `util.parseArgs`, `node:crypto`; понятная ошибка на старом Node.
- Плохо: только erasable-синтаксис; старт 127 мс на 40 модулях TS (55 мс для собранного JS, 53 мс с тёплым кешем); пользователь обязан иметь Node ≥ 24.22.2.

### Bun как основной рантайм

- Хорошо: старт 2–12 мс; TS как есть, включая `enum`, параметры-свойства и `namespace`; `bun test` в 10 раз быстрее; кросс-компиляция; `node:sqlite` FTS5 и `util.parseArgs` работают; npm-пакет запускается.
- Плохо: новая runtime-предпосылка; нет встроенной проверки типов; нет флагов разрешений/песочницы; Windows/macOS не проверены; артефакт 104,1 МиБ для linux-x64; `node:test` только через `bun test`; `module.stripTypeScriptTypes` нет.

### Deno как основной рантайм

- Хорошо: старт 20–24 мс; встроенный `deno check`; `deno compile`; настоящая модель разрешений; `node:sqlite` FTS5, `util.parseArgs`, `node:crypto` работают; npm-пакет запускается.
- Плохо: новая runtime-предпосылка; `--allow-*` в каждой команде хука; тесты 2,15 с на 100 тестов (с `--no-check`); Windows/macOS не проверены; бинарник 99,6 МиБ; `import.meta.url` требует `--allow-read`.

### Node для доставки + Bun только для dev-тестов

- Хорошо: быстрые тесты; доставка остаётся на Node; не нужно менять npm-контракт.
- Плохо: второй тулчейн; расхождение «тесты на Bun, релиз на Node»; разработчик обязан ставить Bun; нарушает E.

### Node + Node SEA

- Хорошо: Node не нужен пользователю; один бинарник.
- Плохо: 121 МиБ; ESM-вход в проверенном сценарии не работает, нужен CJS-бандл; кросс-сборка не автоматизирована; старт не быстрее обычного Node.

### Бинарник Bun/Deno как опциональный escape hatch

- Хорошо: снимает предпосылку Node; кросс-сборка работает; OpenSpec показывает рабочий паттерн.
- Плохо: 65–121 МиБ на платформу; первая сборка требует сети/кеша; подпись и нотаризация; отдельная проверка на каждой ОС; нужен только по триггеру C.

### Skills/plugin-канал

- Хорошо: соответствует тому, как распространяются Superpowers, Conductor, BMAD V7 и другие; не требует бинарника.
- Плохо: это канал интеграции с хостом, а не замена CLI; нужны пины версий и защита от дрейфа; у разных хостов разные форматы.

## Conclusion

**Node.js 24.22.2 + TypeScript со стиранием типов + npm-пакет с собранным JS остаётся решением.** Bun и Deno технически жизнеспособны и не провалили проверку API; они отклонены по продуктовым причинам: вторая runtime-предпосылка, отсутствие выигрыша по жёстким критериям B+E, фрикция Deno-прав в хуках, отсутствие typecheck у Bun, непроверенные Windows/macOS. Скорость Bun реальна, но при принятом допущении не является драйвером.

Триггеры пересмотра:

- **B.** Node перестаёт удовлетворять жёсткому требованию: исчезает или деградирует нужный API (`node:sqlite` FTS5, стирание типов), прекращается поддержка нужной ОС/архитектуры, появляется критическая уязвимость без исправления.
- **C.** Появляется продуктовое требование «работать без Node» — например, `vf` должен запускаться в хуках на машинах, где Node нет.

До наступления B или C бинарник не является текущим каналом; skills/plugin — отдельный канал интеграции, не замена CLI.

## Outcomes and traceability

1. **Runtime и язык → ADR-0002.** Node.js `>=24.22.2`; TypeScript с erasable syntax; отдельная проверка типов; собранный JavaScript для npm; Node предполагается у целевого пользователя; Bun/Deno отклонены; триггеры B и C. ADR-0002 дополнен без смены решения.
2. **Платформы и CI → ADR-0003.** Поддержка Linux, macOS и Windows; CI-матрица проверяет продуктовый минимум `24.22.2` и актуальную LTS Node. Минимумы ОС из документации Node трактуются как границы рантайма, а не как полная гарантия приложения. Локальные измерения проведены только в WSL2/Linux; ADR-0003 фиксирует выбранную матрицу и границы доказательства.
3. **Доставка → ADR-0004.** Пилот из клона → первый публичный выпуск `0.x` → npm-пакет для пилота в реальных проектах; npm-пакет содержит собранный JS. Первая публикация вручную с 2FA, последующие — целевой Trusted Publishing/OIDC с явным человеческим разрешением релиза. Standalone-бинарник рассматривается только по триггеру C; skills/plugin — отдельный канал интеграции. ADR-0004 уточняет этапы и релизный контроль без смены основного решения.

## Limitations and open questions

### Limitations

- **macOS и нативный Windows** — не запускались: среда разработки WSL2, доступа к другим машинам нет. Всё, что зависит от ОС, берётся из документации и будет проверено матрицей CI (ADR-0003).
- **Node 26** локально не установлен; поведение стирания типов и кеша на 26 проверяется только в CI.
- **Node SEA** — ESM-вход в проверенном сценарии не заработал; использован CJS-бандл. Кросс-сборка SEA не проверялась.
- **Deno test** с проверкой типов упал из-за отсутствия `npm:@types/node` в фикстуре; с `--no-check` тесты проходят. Это ограничение конфигурации, а не вывод о Deno.
- **Bun 1.4.4** — единственная версия Bun в сравнении; отдельные второстепенные сценарии не повторялись.
- **WSL2 искажает абсолютные времена** (виртуальный диск, планировщик): числа годятся для сравнения вариантов между собой, не как обещание пользователю.
- **Фикстура — не настоящий код**: соотношения устойчивы, но реальное ядро может отличаться по числу модулей, работе с файлами, сетью, stdin/TTY, сигналами, воркерами, SQLite на диске и памяти.
- **Обзор SDD** сделан чтением репозиториев и документации, без установки и запуска. Часть версий/коммитов не перепроверена: Spec Kitty — по коммиту 2026-10-25; Kiro — закрытый код; Agent OS — страница установки закрыта; GSD — документация говорит Node 18+, `package.json` требует Node ≥ 24; BMAD v6 — выборочно.
- **Статистическая значимость** не считалась: приведены медианы и мин–макс, а не доверительные интервалы.
- **npm provenance** и trusted publishing — по документации; проверить можно только после первой публикации.

### Open questions

- **Линтер и форматтер:** выбрать при появлении первого кода, исходя из необходимости type-aware правил.
- **Релизная сборка:** предварительная рекомендация — `tsc`, поскольку он уже нужен для typecheck и даёт стабильный API. Окончательная реализация обязана выполнять артефактный контракт ADR-0004.
- **Версионирование 0.x и автообновление плагина:** определить ближе к релизу/плагину.
- **Node 26:** проверить в CI, не требует локальных замеров.
- **Триггер C:** если он наступит, определить критерии бинарника (размер, подпись, проверка на каждой ОС, набор архитектур) отдельным ADR.
