# ADR-0002: Node.js >=24.22.2 и TypeScript со стиранием типов

## Context and Problem Statement

viaferrata — CLI `vf` для Linux, macOS и Windows, который запускают люди и хуки агентов. Целевой пользователь — разработчик, у которого Node.js уже есть; если его нет, пользователь устанавливает Node. Для проекта важнее один переносимый артефакт, простота доставки и предсказуемость на трёх ОС, чем скорость запуска. Node.js умеет запускать TypeScript со стиранием типов без отдельной транспиляции, но его поддерживаемый синтаксис ограничен, а запуск исходников из `node_modules` не подходит для опубликованного пакета. Альтернативы Bun и Deno технически жизнеспособны, но добавляют вторую runtime-предпосылку.

## Decision Drivers

- Node.js предполагается у целевого пользователя; если его нет — пользователь устанавливает Node. Это принятый риск, а не задача бинарника.
- Одна runtime-предпосылка и один тулчейн; npm как основной канал доставки.
- Ноль runtime-зависимостей и нативных модулей.
- Один артефакт для поддерживаемых ОС и архитектур.
- Разработка и тесты без сборки; проверка типов отдельно.
- Предсказуемое поведение на Linux, macOS и Windows; понятное сообщение при неподдерживаемой версии Node.
- Скорость запуска и тестов — желательное, но не главное свойство.

## Considered Options

- Node.js + TypeScript со стиранием типов в разработке и сборкой JS для npm.
- Bun как основной рантайм.
- Deno как основной рантайм.
- Node.js для доставки + Bun только для dev-тестов.
- Node.js + Node SEA (standalone-бинарник).
- Bun/Deno `--compile` как опциональный бинарник — аварийный выход по триггеру C.
- Node.js + JavaScript с JSDoc.
- TypeScript с транспиляцией на лету или сборкой на каждый запуск.

## Decision Outcome

Chosen option: **Node.js + TypeScript со стиранием типов в разработке, собранный JavaScript для npm**. Он сохраняет Node/npm как единственную runtime-предпосылку, позволяет запускать исходники без сборки и не требует runtime-зависимостей.

- **Runtime:** Node.js `>=24.22.2`, зафиксированный в `engines.node` и `.node-version`. Это минимальная поддерживаемая версия продукта, а не ограничение «только Node 24» и не обещание навсегда сохранить этот минимум. При его повышении проверяются срок поддержки Node, совместимость и CI-матрица; изменение фиксируется отдельно.
- **Модули и синтаксис:** только ESM; исходные относительные импорты используют `.ts`, импорты типов — `import type`. Код ограничен синтаксисом, который Node может стирать без преобразования runtime-семантики. TypeScript-конфигурация обеспечивает эту границу; конкретные флаги и проверки определяются конфигурацией и CI.
- **Разработка:** исходный TypeScript запускается непосредственно Node. Проверка типов выполняется отдельно через `tsc --noEmit`. Версия компилятора закрепляется lockfile и может обновляться как dev-инструмент; смена компилятора сама по себе не требует ADR, пока соблюдается контракт исходников и артефакта.
- **Входная точка:** `bin/vf.mjs` — JavaScript, который проверяет минимальную версию Node до динамической загрузки `src/cli.ts`. Это сохраняет понятную ошибку на старом Node.
- **Runtime-зависимости:** отсутствуют. `smol-toml` вендорится с лицензией; front matter разбирается собственным строгим парсером; поиск использует `node:sqlite`/FTS5; аргументы — `util.parseArgs`.
- **Почему не Bun/Deno:** оба технически жизнеспособны — `node:sqlite` с FTS5, `util.parseArgs`, `node:crypto` и `import.meta.url` работают. Отказ продуктовый: вторая runtime-предпосылка; у Bun нет встроенной проверки типов и флагов разрешений; у Deno `--allow-*` добавляется в каждую команду хука; Windows/macOS для обоих не проверены; скорость Bun при принятых допущениях не является драйвером.
- **Бинарники:** Node SEA, `bun build --compile` и `deno compile` не являются текущим каналом. Они дают 65–121 МиБ на платформу, требуют первой сборки с сетью/кешем, подписи и проверки на каждой ОС. Бинарник рассматривается только по триггеру C — продуктовому требованию «работать без Node».
- **Пересмотр:** решение пересматривается по триггеру B (нарушение жёсткого требования Node: исчезновение или деградация нужного API, прекращение поддержки ОС/архитектуры, критическая уязвимость без исправления) или C (продуктовое требование «работать без Node»). Скорость, размер экосистемы и популярность сами по себе триггерами не являются.

### Consequences

- Хорошо: один переносимый артефакт; короткий цикл разработки; нет транспиляции при локальном запуске; меньше runtime-зависимостей и поверхности поставки; зрелые Windows/macOS.
- Плохо: ограничения TypeScript syntax; пользователь обязан иметь Node не ниже заявленного минимума; старт на 40 модулях TS — 127 мс против 11 мс у Bun (55 мс для собранного JS и 53 мс с тёплым кешем); публикация требует преобразования `.ts` в `.js`.
- Риск: минимум Node со временем устареет. Мера: явный `engines.node`, проверка версии в CLI и `doctor`, плановый пересмотр по lifecycle Node.
- Риск: у части пользователей Node может не быть. Риск принят: README и `doctor` говорят об установке; если появится продуктовое требование «работать без Node», включается триггер C.
- Риск: преимущества Bun/Deno (скорость, синтаксис, разрешения) остаются неиспользованными. Мера: сравнительные данные и причины зафиксированы в `R-0001`; пересмотр только по B или C.
- Риск: разработческий запуск и опубликованный JS могут расходиться. Мера: тестировать собранный артефакт и npm-тарбол; контракт сборки вынесен в ADR-0004.

### Confirmation

- CI запускает typecheck и тесты на матрице платформ/версий Node (ADR-0003).
- Отдельная проверка подтверждает, что версия Node ниже минимума даёт понятное сообщение и код ошибки.
- Пакет из тарбола запускается без runtime-зависимостей и не содержит исходные `.ts` (ADR-0004).
- При каждом мажорном обновлении Node проверяются триггеры B и C; смена решения без них не выполняется.

## Pros and Cons of the Options

### Node.js + TypeScript со стиранием типов

- Хорошо: запуск исходников без сборки; Node/npm как единая предпосылка; отсутствие runtime-зависимостей; зрелые Windows/macOS; нужные API (`node:sqlite` FTS5, `util.parseArgs`, `node:crypto`) работают.
- Плохо: только erasable-синтаксис; `.ts` в `node_modules` не является допустимым релизным форматом; старт медленнее Bun.

### Bun как основной рантайм

- Хорошо: старт 2–12 мс; TypeScript как есть, включая `enum`, параметры-свойства и `namespace`; `bun test` в 10 раз быстрее; кросс-компиляция; npm-пакет запускается.
- Плохо: вторая runtime-предпосылка; нет встроенной проверки типов; нет флагов разрешений/песочницы; Windows/macOS не проверены; артефакт 104,1 МиБ для linux-x64; `node:test` только через `bun test`; `module.stripTypeScriptTypes` отсутствует.

### Deno как основной рантайм

- Хорошо: старт 20–24 мс; встроенный `deno check`; `deno compile`; настоящая модель разрешений; npm-пакет запускается.
- Плохо: вторая runtime-предпосылка; `--allow-*` в каждой команде хука; тесты 2,15 с на 100 тестов (с `--no-check`); Windows/macOS не проверены; бинарник 99,6 МиБ; чтение ресурса через `import.meta.url` требует `--allow-read`.

### Node.js для доставки + Bun только для dev-тестов

- Хорошо: быстрые тесты; доставка остаётся на Node; npm-контракт не меняется.
- Плохо: второй тулчейн; расхождение «тесты на Bun, релиз на Node»; разработчик обязан ставить Bun; нарушает простоту доставки.

### Node.js + Node SEA

- Хорошо: пользователю не нужен Node; один бинарник.
- Плохо: 121 МиБ; ESM-вход в проверенном сценарии не работает, нужен CJS-бандл; кросс-сборка не автоматизирована; старт не быстрее обычного Node.

### Bun/Deno `--compile` как опциональный бинарник

- Хорошо: снимает предпосылку Node; кросс-сборка работает; OpenSpec показывает рабочий паттерн.
- Плохо: 65–121 МиБ на платформу; первая сборка требует сети/кеша; подпись и нотаризация; отдельная проверка на каждой ОС; нужен только по триггеру C.

### Node.js + JavaScript с JSDoc

- Хорошо: нет ограничений TypeScript stripping.
- Плохо: типы менее выразительны и менее удобны для авторства/рефакторинга.

### TypeScript с транспиляцией на лету или сборкой при каждом запуске

- Хорошо: доступен полный синтаксис TypeScript.
- Плохо: дополнительные инструменты, шаги или runtime-зависимости; хуже старт и больше поверхность поставки.
