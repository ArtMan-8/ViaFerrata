# ADR-0004: Доставка — клон до релиза, npm-пакет с собранным JS после

## Context and Problem Statement

До первого публичного выпуска инструмент нужен самому репозиторию; после — другим проектам. Node не запускает TypeScript из `node_modules`, а симлинки на клон ненадёжны на Windows. Для инструмента, который сам входит в цепочку поставок, важно сохранять проверяемый артефакт и ограничивать число каналов доставки. Целевой пользователь — разработчик, у которого Node уже есть; отдельный standalone-бинарник не является текущей необходимостью.

## Decision Drivers

- Один способ запуска на трёх ОС, без глобальной установки и симлинков.
- Пин версии и проверяемый артефакт.
- Ноль runtime-зависимостей и единый артефакт для ОС.
- Публикация разрешается человеком; CI автоматизирует подготовку и проверки.
- Простота цепочки поставки; второй канал добавляется только по подтверждённой потребности.
- Бинарники — аварийный выход по триггеру C; skills/plugin — отдельный канал интеграции, а не замена CLI.

## Considered Options

- Клон до релиза; npm-пакет с собранным JS после.
- Git-зависимость со сборкой в `prepare`.
- Публикация TypeScript-исходников как есть.
- Один bundle-файл.
- Бинарники под каждую ОС/архитектуру (Node SEA, `bun build --compile`, `deno compile`).
- npm как основной канал плюс опциональный standalone-бинарник по триггеру C.
- Сразу Homebrew, winget и apt.
- Skills/plugin-канал как отдельная интеграция с хостом.

## Decision Outcome

Chosen option: **прямой запуск из клона до релиза и npm-пакет с собранным JavaScript после**. Это предпочтительный путь при текущих ограничениях; пересмотр возможен при доказанной потребности в другом канале.

- **Этапы:** сначала пилот из клона для разработки ViaFerrata; затем первый публичный выпуск `0.x`; после него — пилот npm-пакета в реальных проектах. Это последовательность внедрения, а не три параллельных канала поддержки.
- **До npm-релиза:** запуск `node <clone>/bin/vf.mjs`; путь к клону хранится в локальной настройке машины/проекта, симлинки не требуются.
- **Пакет:** `viaferrata` в npm, ESM, команда `vf` через `bin/vf.mjs`, собранный JavaScript в `dist`, `engines.node >= 24.22.2`, без runtime `dependencies`. Вендоренная библиотека и её LICENSE входят в пакет.
- **Артефактный контракт:** пакет содержит JavaScript, а не исполняемые `.ts`-исходники; относительные импорты разрешаются после сборки; сборка и упаковка воспроизводимы и проверяются установкой из фактического tarball. Инструмент сборки — деталь реализации, пока контракт соблюдён.
- **Версии:** 0.x до стабилизации; версия в `package.json` совпадает с git tag. Потребитель фиксирует точную версию в профиле.
- **Решение о публикации:** CI выполняет сборку, тесты и подготовку артефакта. Человек явно разрешает публикацию через защищённое окружение/подтверждение или ручной запуск из разрешённого workflow. Автоматизация проверки и provenance не означает автоматического разрешения релиза.
- **Доверие к публикации:** первая публикация выполняется вручную с 2FA. Для последующих релизов целевой механизм — npm Trusted Publishing/OIDC и provenance; точные настройки workflow и release-процедура определяются при реализации. CI-подготовка и provenance сами по себе не дают разрешения публиковать: релиз остаётся явно одобренным человеком.
- **Опциональный бинарник:** `bun build --compile`, `deno compile` или Node SEA рассматриваются только по триггеру C — продуктовому требованию «работать без Node». При его наступлении нужен отдельный ADR с критериями: размер (по замерам 65–121 МиБ на платформу), первая кросс-сборка с сетью/кешем, подпись и нотаризация, проверка каждого файла на своей ОС, набор архитектур. Сейчас бинарник не публикуется.
- **Skills/plugin-канал:** набор skills/commands для хоста — отдельный канал интеграции, а не замена CLI. Версии закрепляются, автообновление не предполагается; дрейф между сгенерированными файлами и версией `vf` контролируется проверкой.
- **Не на старте:** отдельные бинарники и дополнительные каналы (Homebrew, winget, apt); пересмотр после обратной связи с реальных проектов.

### Consequences

- Хорошо: один путь запуска на всех ОС; точная версия; проверяемый tarball; меньше каналов поставки; npm-пакет запускается и в Node, и в Bun/Deno, что оставляет путь для будущего.
- Плохо: до релиза обновление через git; после — осознанное обновление версии; релиз требует человеческого действия.
- Риск: пакет и dev-режим могут разойтись. Мера: CI проверяет собранный артефакт и установку из tarball.
- Риск: изменение entrypoint ломает хуки. Мера: закреплённый контракт `bin/vf.mjs` и тест упаковки.
- Риск: бинарник понадобится раньше, чем появится триггер C. Мера: путь описан, критерии и стоимость известны; отдельный ADR не создаётся до наступления C.
- Риск: skills/plugin-файлы разойдутся с версией CLI. Мера: пин версии, генерация из одной модели, проверка в CI.

### Confirmation

- CI устанавливает tarball в чистый проект и запускает CLI напрямую через Node.
- Tarball содержит `bin` и `dist`, не содержит исходные `.ts` и runtime dependencies; поля `bin` и `engines.node` соответствуют контракту.
- Публикация невозможна из произвольной ветки без разрешения человека.
- После выпуска provenance доступна на странице npm-пакета.
- Если наступил триггер C, бинарник проверяется отдельным ADR: сборка, запуск на каждой ОС, checksums, подпись; до этого бинарник не считается каналом.

## Pros and Cons of the Options

### Клон до релиза, npm с собранным JS после

- Хорошо: работает на всех ОС, без глобальной установки/симлинков; единая форма entrypoint; npm-пакет запускается в Node, Bun и Deno.
- Плохо: требует сборки для npm и ручного обновления версии потребителем.

### Git-зависимость со сборкой в `prepare`

- Хорошо: потребитель устанавливает напрямую из репозитория.
- Плохо: сборка на машине потребителя, dev-зависимости/сеть, менее проверяемый артефакт.

### TypeScript-исходники как есть

- Хорошо: нет шага сборки.
- Плохо: Node не запускает `.ts` внутри `node_modules` в выбранном режиме.

### Один bundle-файл

- Хорошо: меньше файлов.
- Плохо: нужен bundler и его конфигурация; выигрыш не обоснован текущим размером пакета.

### Бинарники под каждую ОС/архитектуру

- Хорошо: Node не требуется; старт Bun-бинарника 6,8 мс, Deno — 19,7 мс.
- Плохо: 65–121 МиБ на платформу; отдельная сборка, проверка, подпись и публикация для каждой комбинации; кросс-сборка требует сети/кеша.

### npm + опциональный standalone-бинарник по триггеру C

- Хорошо: основной путь остаётся простым; известен и проверен аварийный выход; OpenSpec использует тот же паттерн.
- Плохо: два артефакта и два набора проверок, если триггер наступит; бинарник нужно поддерживать отдельно.

### Homebrew, winget и apt сразу

- Хорошо: привычные системные каналы.
- Плохо: несколько каналов обслуживания до подтверждения спроса; формула Homebrew у OpenSpec всё равно зависит от Node.

### Skills/plugin-канал

- Хорошо: соответствует распространению Superpowers, Conductor, BMAD V7 и других; не требует бинарника; работает поверх CLI.
- Плохо: не заменяет CLI; у хостов разные форматы; нужны пины версий и защита от дрейфа.
