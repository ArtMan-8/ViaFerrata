# ADR-0001: Pull request как единица проверки и утверждения

## Context and Problem Statement

Репозиторий публичный, с ним работают люди и агенты. Нужен процесс, который:

- оставляет в `trunk` только проверенное и принятое;
- даёт одну точку утверждения, которую агент не может обойти;
- замораживает спецификацию задачи до начала реализации;
- сохраняет линейную историю и машиночитаемые имена веток и файлов.

Прямые коммиты в `trunk` этого не дают: у агента есть право записи, а проверки в хуках и CI обходятся локально.

## Decision Drivers

- Утверждает человек; агент готовит артефакты и код, но не сливает.
- Проверки должны быть воспроизводимы вне сессии агента.
- Спецификация задачи замораживается после утверждения; реализация не может менять её молча.
- История `trunk` линейная, без merge-коммитов.
- Имена веток и файлов проверяемы по префиксам и регулярным выражениям.

## Considered Options

- Прямые коммиты в `trunk`.
- Защищённый `trunk` и один pull request на задачу.
- Защищённый `trunk` и два pull request на задачу: спецификация и реализация.
- Долгоживущие ветки и GitFlow.

## Decision Outcome

Chosen option: "Защищённый `trunk` и два pull request на задачу: спецификация и реализация", because только этот вариант отделяет утверждение «что делать» от приёмки реализации и оставляет спецификацию замороженной.

- `trunk` защищён: требуется pull request, линейная история, запрет обхода правил администраторами.
- Единица работы — pull request. Слияние выполняет человек с правом записи (мейнтейнер); слияние и есть утверждение.
- Задача — два pull request:
  1. `spec/T-NNNN_<тема>` — только документы: спецификация задачи и, при необходимости, мини-ADR на найденный пробел в решениях;
  2. `impl/T-NNNN_<тема>` — реализация по утверждённой спецификации.
- Спецификация замораживается после слияния первого PR: в ветке реализации файл спецификации не меняется. Уточнения, не противоречащие утверждённому, пишутся в журнал реализации.
- ADR — отдельный pull request только с документами; слияние в `trunk` означает принятие. В `trunk` находятся только принятые ADR.
- Реализация сжимается локально в один коммит и сливается rebase-merge; SHA коммитов в файлах репозитория не хранятся.

### Consequences

- Хорошо: `trunk` всегда в принятом состоянии; утверждение нельзя подделать локально; спецификация заморожена; имена проверяемы регулярными выражениями.
- Плохо: на задачу два PR вместо одного; срочная правка проходит ту же церемонию; rebase-merge меняет SHA коммитов.
- Риск: человек может обойти процесс, сняв защиту ветки; мера — запрет обхода администраторами, позже — журнал гейтов и проверки в CI.

### Confirmation

На этом этапе — настройки защиты `trunk` и ревью в pull request. После реализации инструмента — проверки pre-push и CI: имена веток, «только документы» для `docs/`, `adr/`, `research/`, `spec/`, допуск `impl/` по утверждённой спецификации. `vf check ADR-NNNN` (G0) и `vf check T-NNNN` (G1+G2 для задачи) — локальные проверки; принятие — слияние PR.

## Pros and Cons of the Options

### Прямые коммиты в `trunk`

- Хорошо: нет церемонии.
- Плохо: нет точки утверждения, проверки обходятся, история не гарантирует принятого состояния.

### Один pull request на задачу

- Хорошо: меньше шагов.
- Плохо: смешивает «что делать» и «как сделано»; спецификацию нельзя заморозить до реализации.

### Два pull request на задачу

- Хорошо: утверждение спецификации отделено от приёмки реализации; спецификация заморожена.
- Плохо: два шага и больше времени.

### Долгоживущие ветки и GitFlow

- Хорошо: привычная модель для релизов.
- Плохо: на этом масштабе не нужна; короткие ветки и линейная история проще проверяются.

## More Information

- Формат ADR — MADR 4.0.0: <https://adr.github.io/madr/>. Заголовки разделов — канонические английские, текст — по-русски.
- Шаблоны: `work/templates/adr-full.md` (полный) и `work/templates/adr-minimal.md` (малый); правила — `work/templates/README.md`.
- Статусы: `accepted`, `deprecated`, `superseded by ADR-NNNN[, ADR-NNNN]`. `proposed` и `rejected` не используются: слияние — единственное изменение состояния, отклонённый ADR в `trunk` не попадает.
- Схема имён: `<вид>/<тема>`; виды — `docs`, `adr`, `research`, `spec`, `impl`; тема — kebab-case; подчёркивание отделяет идентификатор от темы или вида файла.
- `applies_to: ["**"]` — решение действует для всех файлов репозитория; `core: true` — ADR всегда попадает в пакет контекста.
- Роли: мейнтейнер и утверждающий — всегда люди; агентские роли `verifier` и `reviewer` проверяют, но не утверждают и не сливают.
- Коммиты — Conventional Commits на английском; заголовок(что сделал) 1 предложение и тело(что сделано) 2–5 строк только если заголовка мало; только индекс (`git commit` без `-a`).
- Дополнение, не меняющее решение, вносится правкой существующего ADR. Замена любой части решения — новый ADR с полным переизложением; старый получает `status: superseded by ADR-NNNN`, а новый ссылается на него в `More Information`. Отдельных полей `supersedes` и `amends` нет: MADR выражает замену через статус.
