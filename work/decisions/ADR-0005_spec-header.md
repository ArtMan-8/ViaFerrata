# ADR-0005: Шапка и структура спецификации задачи

## Context and Problem Statement

Спецификация задачи — первый документ, который читают человек и агент, и единственный, который замораживается до реализации. Ей нужны машиночитаемые поля для проверок и человекочитаемые разделы, которые не дублируют ADR. Формат шапки до этой задачи оставался черновиком и не был зафиксирован.

## Considered Options

- Спецификация без шапки: только разделы Markdown.
- Минимальная шапка `date`, `scope`, `tests`, `ac` и три раздела: Intent, Specification, Plan.
- Расширенная шапка с `status`, `owner`, `depends_on` и другими служебными полями.

## Decision Outcome

Chosen option: "Минимальная шапка `date`, `scope`, `tests`, `ac` и три раздела", because она даёт проверкам ровно те данные, которые нужны, и не дублирует статус, уже выраженный слиянием PR и именем файла; `date` добавлен для единообразия с ADR и Research.

### Header

Шапка — YAML front matter в начале файла:

```yaml
---
date: "{YYYY-MM-DD}"
scope:
  - glob
tests:
  - glob
ac:
  - { id: AC-1, check: test }
  - { id: AC-2, check: manual }
---
```

* `scope` — непустой построчный список глобов путей (по одному на строку через `-`), которые задача может менять; синтаксис — как в ADR-0001 (`*`, `**`, `?`, `dir/**`, без отрицаний).
* `tests` — непустой построчный список глобов путей тестов через `-`; тот же синтаксис.
* `ac` — непустой список критериев приёмки; `id` уникален и имеет вид `AC-N`; `check` — одно из `test`, `manual`, `metric`.
* Идентификатор задачи в шапке не хранится: он в заголовке `# T-NNNN: <тема>` и в имени файла `T-NNNN_spec.md`.
* `date` — дата спецификации в формате `YYYY-MM-DD`, обновляется при редакции до заморозки; отдельного `status` нет: утверждена = лежит в `trunk`; ответственный — мейнтейнер.

### Body

Разделы и их заголовки:

```markdown
## Intent
### Goal
### Constraints
### Context
### Examples
### Acceptance Criteria

## Specification
### Change boundaries
### Scenarios
### Expected behavior
### Definition of Done

## Plan
### Layers
### Applicable ADRs
```

* `Intent` — пять полей постановки: цель, ограничения, контекст, примеры, критерии приёмки. `Acceptance Criteria` — полное имя раздела; в тексте после первого упоминания допустимо сокращение AC. Каждый AC повторяет ID из списка `ac` и содержит наблюдаемый критерий.
* `Specification` — границы изменения по путям (зеркало `scope`), сценарии G/W/T (Given/When/Then), ожидаемое поведение и задачный Definition of Done. AC и DoD различаются: AC — что должно работать, DoD — что нужно, чтобы результат считался завершённым инженерно.
* `Plan` — последовательность слоёв и применимые ADR по ID; детали реализации — не уровень спецификации.
* Сценарий оформляется как `#### Scenario S-N: <название>` со строками `* **Given** …`, `* **When** …`, `* **Then** …` и необязательным `* **And** …`.
* Каждый AC называет проверяемые сценарии (`Covers: S-N`); каждый сценарий покрыт хотя бы одним AC.
* Заголовки — английские, текст — русский.

### Consequences

* Хорошо: сводка задачи читается машиной без разбора текста; у AC и сценариев есть стабильные ID; формат пригоден для шаблона и проверок.
* Плохо: шапка и тело содержат одни и те же ID и пути; расхождение придётся ловить проверками.
* Риск: со временем понадобится поле вроде `depends_on`. Мера: менять формат новым ADR, а не молчаливой правкой.

### Confirmation

* Первая спецификация задачи оформлена по этому формату.
* Проверки задач и спецификаций (`vf check`) сверяют дату, наборы ID шапки и тела, непустоту и синтаксис глобов, наличие разделов и тип проверки у каждого AC.
* На этапе ручного процесса соответствие проверяется при ревью PR 1.
