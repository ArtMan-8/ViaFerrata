# Работа в ViaFerrata

## Назначение и принципы разработки

Мы разрабатываем ViaFerrata — минимальную систему агентной разработки: инструкции, шаблоны, CLI и автоматические проверки. Текущий фокус — соло-разработчик. Система должна помогать превращать намерение человека в проверенное изменение, уменьшать расхождение требований и кода и сохранять контекст между сессиями.

Основа — intent-centric подход: явная цель, достаточный контекст, автономное исполнение и проверяемый результат.

При развитии ViaFerrata:

- **Уменьшай работу человека.** Агент готовит и актуализирует документы, CLI автоматизирует формальные операции и проверки. Не перекладывай служебные поля, синхронизацию и повторные подтверждения на пользователя.
- **Сохраняй соразмерность процесса.** `vibe/deep` определяет формализацию задачи, `lite/strict` — профиль автоматического контроля проекта. Не превращай strict в дополнительные ручные ритуалы, а vibe — в освобождение от требований и проверок.
- **Добавляй только необходимое.** Новый документ, поле, команда, зависимость или этап должны решать конкретную проблему. Сначала используй существующие механизмы; оценивай стоимость сопровождения. Research и ADR создаются по необходимости.
- **Поддерживай требования вместе с реализацией.** SRS хранит действующие обязательства, changes — историю изменений. Обновляй затронутые требования, код и проверки в одной работе; не переписывай историю и не превращай обнаруженное поведение автоматически в норму.
- **Разделяй возможности и гарантии.** Инструкции направляют агента, CLI проверяет формализованные свойства, среда обеспечивает права и изоляцию. Структурная валидность не доказывает правильность поведения. Не выдавай запланированную автоматизацию за реализованную.
- **Делай контекст компактным, а продолжение — надёжным.** Точки входа дают краткую ориентацию; детали загружаются по необходимости. Для возобновления должно хватать актуальных документов и состояния задачи без чтения всей переписки.
- **Проверяй пользу на практике.** Используй ViaFerrata при её собственной разработке и учитывай опыт внешнего проекта. Правки инструкций проверяй на реальном проблемном случае и соседнем сценарии. Оценивай уменьшение ошибок, потери контекста и ручных действий.
- **Удерживай текущий масштаб.** Собственный агентный runtime, обязательная многоагентная оркестрация, командные слияния, графовая инфраструктура и расширенный аудит требуют отдельной подтверждённой потребности.

Перед усложнением объясни, какую проблему оно решает, почему существующих средств недостаточно и как проверить пользу. Выбирай самое простое решение, сохраняющее необходимые гарантии.

## Контекст

- Прочитай [README](README.md) и [общие правила](instructions/workflow.md). Комплект задачи находи по правилу обнаружения в общих инструкциях; ссылки на конкретные задачи в AGENTS.md не закрепляй.
- Формы и связи документов — в [руководстве шаблонов](templates/README.md), термины — в [глоссарии](docs/GLOSSARY.md).
- Отложенные идеи и вопросы — в [каталоге идей](viaferrata/ideas/README.md); правила записи и разбора — в общих инструкциях.
- Перед изменениями проверь ветку, Git status и diff. Сохраняй пользовательские изменения; работай в пределах текущего репозитория и согласованного scope.

## Правила работы

- Пиши документы по-русски; стандартные заголовки, поля и ID сохраняй по шаблонам.
- Ведение документов, согласование scope и хранение временных данных описаны в [общих правилах](instructions/workflow.md).
- Перед установкой зависимостей и удалением файлов получи явное разрешение; действующие разрешения текущей задачи проверяй в Journal.
- Коммиты оформляй по Conventional Commits на английском: заголовок о выполненном изменении, при необходимости тело из 2–3 предложений.
- Коммит, публикация и выпуск требуют отдельного поручения.

## Проверки

Выбирай проверки по затронутым областям; для смешанного изменения объединяй применимые строки.

| Изменение                                                   | Проверки                                                                                                                                                                              |
| ----------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Документация                                                | Форматирование и Markdown, ссылки: `npm run format:check`, `npm run lint`, `node --test src/tests/documentation.test.ts`; для документов ViaFerrata — также `node bin/vf.ts validate` |
| TypeScript-код                                              | `npm run lint`, `npm run format:check`, `npm run typecheck` и тесты затронутого поведения; при влиянии на общие компоненты — `npm test`                                               |
| Сборка, метаданные или состав пакета, доступ к ресурсам CLI | `npm run build` и `npm run test:package`                                                                                                                                              |
| Зависимости или lockfile                                    | `npm ci`, оба audit и проверки затронутых компонентов                                                                                                                                 |
| Кандидат выпуска                                            | `npm ci`, lint, format:check, typecheck, test:all, build, validate и оба audit; сценарий поставки проверяет именно публикуемый архив                                                  |

Оба audit — `npm audit` и `npm audit --omit=dev`. High/critical устрани либо получи принятие конкретного риска; остальные замечания разбери в Journal. Изменение только текста поставляемой инструкции требует документальных проверок; проверка архива выполняется при подготовке нового выпуска. Изменение поиска или состава ресурсов требует теста поставки.

Не запускай `lint:fix` и форматирование всего репозитория автоматически: исправляй найденные проблемы в затронутых файлах до итоговой проверки. Правила повторного использования результатов — в [инструкции реализации](instructions/implementation.md#реализация-и-проверки); выбор по таблице не является исключением и не требует отдельного согласования.

Перед завершением выполни `git diff --check` и `git diff --cached --check`, сверь tracked/untracked-файлы со scope и проверь штатную очистку созданных тестовых данных. Запиши результаты и ограничения в Journal для deep-задачи.
