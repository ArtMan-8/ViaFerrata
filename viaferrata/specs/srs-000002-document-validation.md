# Проверка документов и области изменений

## Purpose and Boundaries

Пользователь и агент проверяют структуру документов проекта и пути, изменённые при выполнении deep-задачи. Согласование работы, проверка поведения и решение о завершении требуют отдельных оснований.

## System Overview

Синтаксис команд, вывод и коды завершения описаны в [SRS «CLI-инструменты»](srs-000003-cli-tools.md).

Команда `vf validate` индексирует рабочие и архивные документы, проверяет структуру, идентичность и ссылки. Состав правил и различия профилей определяет [каталог встроенных проверок](srs-000001-built-in-checks.md). Для проверки путей в lite и strict служит отдельная команда `vf scope change-NNNNNN`. Для проверки нужен рабочий комплект. Корень проекта должен совпадать с корнем рабочего дерева Git. Исходный коммит должен быть доступен и входить в историю HEAD. При конфликте индекса, изменённом симлинке или подмодуле команда завершает проверку с ошибкой. Агент сохраняет решение пользователя, исходную базу и сумму согласованных масок по [правилам Journal](../../instructions/journal.md#согласование-и-решения).

Команда `vf complete change-NNNNNN` завершает рабочую deep-задачу после проверки согласованного комплекта, scope и результатов в Journal.

## Requirements

### R-1: Основание проверки

При создании Spec и после каждой дельты агент записывает `scope` в порядке дерева проекта. CLI использует тот же порядок для вычисления суммы. Перестановка строк сохраняет сумму.

Для суммы CLI сортирует копию масок в порядке дерева, сериализует её через `JSON.stringify` без пробелов и вычисляет SHA-256 байтов UTF-8. Отсутствие `scope` соответствует пустому списку. В Significant Events агент хранит YAML-блок `scope_check` с полями `base` (полный SHA исходного коммита) и `digest` (SHA-256 текущего принятого `scope`). В `decisions` агент записывает основание согласования. После принятой дельты агент описывает точное изменение прав и обновляет `digest`, сохраняя `base`. Одного изменения Spec недостаточно. CLI проверяет совпадение суммы; авторство решения и подлинность Journal устанавливает человек или агент.

### R-2: Область разрешённых путей

Путь задаётся относительно корня проекта с разделителем / и сравнивается с учётом регистра. Звёздочка соответствует любой последовательности символов внутри одного компонента, включая точку. Конечное /** разрешает файлы на любой глубине внутри указанной директории. Точный путь разрешает только этот файл. Автоматически разрешены только Intent, Spec, Plan и Journal выбранного change. Эти правила действуют и для новых путей.

### R-3: Проверяемые изменения Git

Команда проверяет объединение путей разности деревьев `base` и HEAD, изменений индекса относительно HEAD, рабочего дерева относительно индекса и неигнорируемых untracked-файлов. Проверяются удалённые пути и обе стороны переноса. Изменения разных слоёв не погашают друг друга. Проверка проходит, когда все слои прочитаны и каждый обнаруженный путь разрешён.

### R-4: Типизированные отношения

В lite и strict validate проверяет распознанные отношения по всем документам индекса, включая входящие из неизменённых файлов. Covers допускает AC → R задачной Spec или SRS, S задачной Spec → AC или R, S из SRS → R из SRS, P → AC, R, S или DOD. Verifies связывает V с AC, R, S, DOD или целым ADR. Changes задаётся полем changes действующей YAML-дельты R задачной Spec и указывает R SRS. Для add сохраняется исключение будущей цели. Для Covers, Depends on и Verifies используются списки ссылок соответствующего элемента по шаблонам. Обычные упоминания и примеры кода не образуют отношений. Ошибка типа указывает источник, отношение и цель и даёт ненулевой код возврата. Полнота актуальной формы архива не проверяется.

### R-5: Самоссылки и циклы

Самоссылка в типизированном отношении является ошибкой. Depends on связывает два шага одного Plan. Ссылка на шаг другого change является ошибкой. Supersedes связывает целые документы одного типа из Intent, SRS, Research и ADR. CLI выявляет циклы отдельно в Depends on и supersedes, сообщает участвующие адреса и возвращает ненулевой код. Обратные ссылки вычисляются из прямых.

### R-6: Безопасный переход

На согласованном рабочем комплекте с `execution in_progress` команда `vf complete change-NNNNNN` проверяет наличие Intent, Spec и Plan со статусом approved, Journal с записанным основанием согласования и заполненным итогом, закрытие шагов P-* и результат проверки границ по правилам `vf scope`. Переход требует сохранения сторонних правок Plan. Обнаруженная конкурентная правка препятствует записи.

### R-7: Обязательные проверки

В разделе Definition of Done задачной Spec агент перечисляет применимые проектные проверки в YAML-списке completion_checks. Каждый элемент соответствует точному значению subject в checks текущего Journal. Для каждого обязательного subject нужен однозначный текущий результат passed с источником и известной редакцией входов. Отсутствие результата, конфликт текущих записей, неизвестный исход, failed и blocked препятствуют завершению. Агент устанавливает применимость результата к текущим входам и сохраняет основание в Journal. CLI читает отчёт агента или CI.

### R-8: Проверка каждого AC

При включённом verification-coverage для каждого AC целевого Intent нужен Verifies из V того же Journal с известной Revision и результатом passed для этой проверки. Поле `verification` записи `checks` указывает локальный ID V. Один V может проверять несколько AC. В обычном `lite` пропущенный Verifies сам по себе допуска не блокирует. У агента сохраняется обязанность проверить каждый AC.

### R-9: Сохранение согласованной политики

При согласовании агент фиксирует в Journal основание решения и контрольную сумму согласованного перечня completion_checks. Команда сверяет перечень с этим основанием и учитывает политику встроенных проверок исходной базы scope. До первой задачи подключение и настройки проекта фиксируются в Git. Для завершения базовый коммит должен содержать viaferrata.toml. Ослабление профиля ради завершения текущего change запрещено. Принятую дельту проверок агент отражает в Spec и Journal в том же change. Следствия уже принятой дельты отдельного решения не требуют.

### R-10: Действие правил во времени

Команда проверяет целевой рабочий комплект и ошибки, мешающие разрешить его зависимости. Индекс включает архивные ID. vf validate сохраняет проектный охват целостности. Новые условия перехода применяются при завершении целевого change. Прежняя форма архива пропускается, конкретное расхождение формы завершённого неархивного документа может дать предупреждение. Агент показывает предупреждение пользователю. Если успешный полный validate входит в completion_checks, его результат обязателен. Синхронизация SRS и архивирование следуют после перехода.
