# Встроенные правила проверки ViaFerrata

## Purpose and Boundaries

Эта SRS определяет, какие правила выполняет `vf validate` в профилях lite и strict и как проект включает дополнительное правило. Покрытие требования шагом Plan подтверждает наличие плана его реализации. За проверку поведения отвечают агент и CI. Выбор проверок и условия завершения описаны в [инструкции реализации](../../instructions/implementation.md), запись результатов — в [правилах Journal](../../instructions/journal.md).

## System Overview

| Проверка                                                                      | lite                                  | strict |
| ----------------------------------------------------------------------------- | ------------------------------------- | ------ |
| Core: конфигурация, структура и комплектность документов, ID, дельты и ссылки | Всегда                                | Всегда |
| `plan-requirement-coverage`: покрытие R рабочей Spec шагами Plan              | При включении через `required_checks` | Всегда |

## Requirements

### R-1: Конфигурация проверок и пределы автоматизации

CLI принимает required_checks как список ID дополнительных встроенных правил. Отсутствующее поле и пустой список оставляют профиль без дополнений. Базовые проверки конфигурации, структуры, идентичности и ссылок действуют в обоих профилях. Правило plan-requirement-coverage входит в strict и может быть включено в lite. Неизвестный ID или неверный тип даёт E_CONFIG; повторный выбор одного правила оставляет его включённым однократно. Команды init, new и validate используют общую конфигурацию. Поведение protected_paths сохраняется.

### R-2: Покрытие требований рабочей Spec

При включённом plan-requirement-coverage команда validate проверяет каждый объявленный R рабочей Spec. В том же deep-комплекте у шага P должна быть явная связь Covers на этот R либо на AC Intent, у которого есть Covers на этот R. Отсутствие покрытия даёт E_PLAN_COVERAGE с адресом требования и ненулевой код завершения. Примеры кода, текстовые упоминания и связи другого change покрытия не дают. В архиве правило не применяется. В vibe отсутствие комплекта допустимо. Покрытие описывает план работ; проверку поведения выполняет агент или CI средствами проекта.

## Verification

Для [srs-000001/R-1] сравнить один комплект с пропущенным R в lite, lite с явно включённым правилом и strict с пустым списком. Проверить неизвестный ID правила и обнаружение битой ссылки в lite.

Для [srs-000001/R-2] восстановить покрытие сначала напрямую, затем через AC того же change. Проверить упоминание в тексте, ссылку через чужой AC, архивный комплект и проект без deep-комплекта. [CLI-сценарии](../../src/tests/validation.test.ts).
