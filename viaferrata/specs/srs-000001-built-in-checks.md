# Встроенные правила проверки ViaFerrata

## Purpose and Boundaries

Эта SRS определяет, какие правила выполняет `vf validate` в профилях lite и strict и как проект включает дополнительное правило. Покрытие требования шагом Plan подтверждает наличие плана его реализации. За проверку поведения отвечают агент и CI. Выбор проверок и условия завершения описаны в [инструкции реализации](../../instructions/implementation.md), запись результатов — в [правилах Journal](../../instructions/journal.md).

## System Overview

Вызовы команд и результаты для пользователя описаны в [SRS «CLI-инструменты»](srs-000003-cli-tools.md).

Каталог указывает коды сообщений команды validate. Пометка «Всегда» означает, что правило входит в core обоих профилей и действует при указанных условиях. Конфигурацию проверяют также init и new. При создании комплекта или самостоятельного документа команда new проверяет идентичность документов и учитывает архив. Служебные ошибки чтения и выполнения имеют собственные коды.

## Requirements

### R-1: Конфигурация проверок и пределы автоматизации

CLI принимает required_checks как список ID дополнительных встроенных правил. Отсутствующее поле и пустой список оставляют профиль без дополнений. Базовые проверки конфигурации, структуры, идентичности и ссылок действуют в обоих профилях. Правило plan-requirement-coverage входит в strict и может быть включено в lite. Неизвестный ID или неверный тип даёт E_CONFIG; повторный выбор одного правила оставляет его включённым однократно. Команды init, new и validate используют общую конфигурацию. Ключ protected_paths отклоняется как неизвестный при любом значении.

### R-2: Покрытие требований рабочей Spec

При включённом plan-requirement-coverage команда validate проверяет каждый объявленный R рабочей Spec. В том же deep-комплекте у шага P должна быть явная связь Covers на этот R, на AC Intent либо на S задачной Spec, откуда до этого R ведёт цепочка явных Covers. Допустимые пути: P → R, P → AC → R, P → S → R и P → S → AC → R. Отсутствие покрытия даёт E_PLAN_COVERAGE с адресом требования и ненулевой код завершения. Примеры кода, текстовые упоминания и связи другого change покрытия не дают. В архиве правило не применяется. В vibe отсутствие комплекта допустимо. Покрытие описывает план работ; проверку поведения выполняет агент или CI средствами проекта.

### R-3: Публичный ID в диагностике

Каждое самостоятельное проверяемое условие встроенной валидации имеет публичный ID. При нарушении правила CLI выводит его ID вместе с существующим кодом диагностики. Для одного нарушения конфигурации init, new и validate выводят один и тот же ID. Ошибки ввода-вывода и другие сбои выполнения сохраняют собственную диагностику. Уровни сообщений, коды завершения, условия применения правил и допустимые значения TOML сохраняются.

### R-4: Каталог встроенных правил

SRS встроенных проверок содержит таблицы по областям. Каждому публичному ID соответствует одна строка с проверяемым условием, областью применения, порядком включения в профилях и кодами диагностики. Для рабочих и архивных документов каталог указывает применимые различия. README и руководство быстрого старта ведут к каталогу.

### R-5: Область применения публичных правил

CLI выводит действующие ID из каталога. Для полей scope и списков ссылок действуют разные правила. Режим выполнения волны и наличие шагов проверяются независимо. Для комплекта с архивными документами целостность переноса и конечное состояние Plan также проверяются независимо. При нарушении обоих условий CLI выдаёт обе диагностики. Правила размещения локальных объявлений и обязательных разделов учитывают частные случаи Journal и ADR. Текст сообщения указывает конкретный подраздел или нарушенное условие.

### R-6: Код диагностики встроенного правила

Определение каждого встроенного правила связывает его публичный ID с одним итоговым кодом диагностики. При нарушении правила CLI берёт ID и код из определения. Сообщение поясняет конкретное нарушение. Расположение документа определяет применимость проверки формы.

### R-7: Явное покрытие AC проверками

В strict для рабочего deep-комплекта с execution in_progress validate перечисляет адреса AC текущего Intent без прямой ссылки Verifies из V его Journal. Для каждого такого AC выдаётся предупреждение, которое само по себе не меняет код возврата. В lite проект может включить ту же проверку через required_checks. Редакцию всех целей записи V задаёт её поле Revision. При отсутствии значения редакция неизвестна, явная связь сохраняется. Состояние checks, связи Covers и Changes не подтверждают результат или редакцию проверки. Это правило сообщает о структурном покрытии и не определяет допуск к completed.

## Verification

Для [srs-000001/R-1] сравнить один комплект с требованием R, которое не покрывает ни один шаг Plan, в lite, lite с явно включённым правилом и strict с пустым списком. Проверить неизвестный ID правила и обнаружение битой ссылки в lite.

Для [srs-000001/R-2] проверить четыре пути одного change: P → R, P → AC → R, P → S → R и P → S → AC → R. Проверить упоминание в тексте, ссылку через чужой AC, архивный комплект и проект без deep-комплекта. [CLI-сценарии](../../src/tests/validation.test.ts).

Для [srs-000001/R-3] сравнить ID сообщения о неверном профиле у команд `init`, `new` и `validate`. Для [srs-000001/R-4] сопоставить строки каталога с определениями в коде и проверить область применения правил на рабочем и архивном документе.

Для [srs-000001/R-5] сравнить рабочий и архивный документы с ошибками в scope и origin. Проверить отдельные и одновременные нарушения в волне и архивируемом комплекте, а также общий ID и точный подраздел в сообщениях для Journal и ADR.

Для [srs-000001/R-6] сверить пары ID и кода в таблицах с определениями. Проверить диагностику полей состояния и применение правил формы в архиве.

Для [srs-000001/R-7] сравнить два AC при одном Verifies, затем добавить вторую цель и убрать Revision. Проверить strict и явное включение в lite.
