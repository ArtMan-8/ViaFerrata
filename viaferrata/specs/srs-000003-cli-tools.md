# CLI-инструменты

## Purpose and Boundaries

Пользователь и агент вызывают `vf` для подключения проекта, создания комплектов и самостоятельных документов, проверки документов, чтения результатов и завершения deep-задачи. Эта SRS определяет поддерживаемые вызовы, входы, результаты и изменения файлов.

## System Overview

Для подключения нужны CLI и существующий каталог. Проект хранит настройки в `viaferrata.toml`. В [каталоге правил](srs-000001-built-in-checks.md) описаны конфигурация и диагностики, в [SRS проверки документов и области изменений](srs-000002-document-validation.md) — правила `scope` и допуска к `completed`. [Руководство подключения](../../docs/quickstart.md) показывает путь от установки до первой задачи.

## Requirements

### R-1: Вызовы, справка и версия

В поддерживаемой среде Node.js 24.x вызовы `vf` и `vf --help` выводят справку со всеми командами и абсолютными путями к `instructions/workflow.md` и `templates/README.md` из запущенной установки. `vf --version` выводит версию установленного пакета. Для этих вызовов конфигурация не требуется, файлы сохраняются, код успеха 0. Опции `--help` и `--version` используются самостоятельно. Неизвестная команда или неверный самостоятельный вызов глобальной опции дают `E_CLI_SYNTAX` с подсказкой «см. `vf --help`». Для распознанной команды ошибки синтаксиса, включая неизвестную или повторную опцию, неверные значения аргументов и лишние аргументы, дают `E_CLI_COMMAND_USAGE` с поддерживаемым синтаксисом команды. Обе диагностики выводятся в `stderr`, код завершения 2, файлы сохраняются. Неподдерживаемая версия запущенного Node даёт `E_RUNTIME` и код 2.

Команды `new`, `validate`, `summary` по ID, `scope` и `complete` выбирают ближайший `viaferrata.toml` вверх от `cwd`. Отсутствие проекта или ошибка найденной конфигурации останавливают команду с кодом 2. Диагностика в `stderr` указывает место, код, причину и способ исправления. При передаче диагностики встроенного правила команда сохраняет исходный код, публичный ID правила, путь, строку и столбец. Команда, которой требуется конкретный комплект или документ, сообщает `E_DOCUMENT_NOT_FOUND`, если запрошенный артефакт отсутствует в области поиска. Отсутствие адресата ссылки при проверке документа по-прежнему даёт `E_REFERENCE_TARGET`.

### R-2: Выбор каталога и конфигурации init

`vf init [path] [--profile lite|strict] [--documents-root <path>]` подключает существующий каталог `path` относительно `cwd` либо сам `cwd`. Корень Git автоматически не определяется. Обе опции принадлежат только `init`, допускаются по одному разу до или после команды, со значением через пробел или знак равенства.

Первое подключение внутри уже подключённого проекта запрещено. Для создания TOML требуется явный профиль. Если профиль пропущен, CLI до записи возвращает `E_CONFIG` и код 2. В `stderr` он кратко объясняет выбор: `lite` включает базовые проверки документов, `strict` дополнительно проверяет покрытие требований шагами Plan и критериев приёмки записями Journal в deep-задачах. Подсказка даёт оба вызова с `--profile`.

При повторном `vf init` без опций используется профиль существующего TOML. При создании конфигурации без `--documents-root` в TOML записывается только строка `profile` с LF. Корень документов по умолчанию — `viaferrata/`. Если при создании конфигурации задан `--documents-root`, команда записывает значение аргумента в строковое поле `documents_root`. При чтении TOML сохраняются все символы исходного пути, включая пробелы и кавычки.

К аргументу применяются правила `documents_root` каталога встроенных проверок и проверка совместимости пути с файлами подключения. Корень отсчитывается от проекта. При существующем TOML используются его настройки. Явный профиль должен совпадать. После проверки исходного аргумента корни сравниваются как пути с нормализованными разделителями. Иное написание того же пути сохраняет исходный TOML. Несовпадающий профиль или корень и недопустимое значение пути дают `E_CONFIG` до записи, отсутствие значения опции в вызове `init` даёт `E_CLI_COMMAND_USAGE`. `init` сохраняет существующие документы на месте.

### R-3: Файлы подключения и восстановление

`init` создаёт или дополняет только `viaferrata.toml`, `AGENTS.md` и `.gitignore`. В `AGENTS.md` добавляется один штатный блок навигации к инструкциям выбранной установки. Блок указывает, как найти `workflow.md` через справку выбранной установки. Ручной текст вне блока сохраняется, сравнение штатного тела допускает LF и CRLF. Ранее поставленные штатные блоки принимаются. Изменённый, непарный, переставленный или повторённый маркер требует разрешения конфликта. Для временного каталога добавляется строка `/.viaferrata/`. Самостоятельная строка с начальным слешем или без него достаточна. Более позднее отрицание требует ручной проверки. При добавлении исходные байты сохраняются префиксом с подходящим разделителем строк.

Неподдерживаемая кодировка дополняемого файла даёт `E_UNSUPPORTED`. `init` сохраняет BOM, существующие переводы строк и права дополняемого файла. До первой записи `init` проверяет конфигурацию, доступность ресурсов пакета, типы путей и все три файла подключения. Симлинк даёт `E_UNSUPPORTED`, несовместимый тип файла подключения или конфликт блока дают `E_CONFLICT`. Пересечение корня документов с файлом подключения и файл на месте каталога документов дают `E_CONFIG`. Проверяемый конфликт сохраняет состояние проекта. Перед записью проверяется конкурентное изменение. Изменения применяются в порядке `.gitignore`, `AGENTS.md`, новая конфигурация. При обработанном сбое временные файлы операции очищаются, ошибка очистки диагностируется. При сбое записи CLI указывает проблемный путь, уже выполненные изменения и способ продолжения. После исправления причины повтор дополняет недостающее. Готовые файлы сохраняют байты и `mtime`.

При успехе, в том числе при повторе, код 0. В `stdout` выводятся абсолютные корни проекта и документов, профиль, действие для каждого файла, пути к инструкциям и руководству форм. Подсказка предлагает открыть проект с агентом, назвать цель задачи и ожидаемый результат. При отказе код 2, причина в `stderr`.

### R-4: Создание черновиков

Команда принимает тип и одно непустое однострочное название: `vf new change "Название"`, `vf new srs "Название"`, `vf new adr "Название"` или `vf new research "Название"`. Название с префиксом `--` запрещено. При ошибке аргументов CLI выводит в `stderr` `E_CLI_COMMAND_USAGE` с формой выбранного типа или всеми четырьмя формами, если тип неизвестен или пропущен, возвращает 2 и сохраняет дерево файлов.

Команда проверяет индекс идентичности рабочих и архивных документов. Для каждого типа отдельно выбирает номер после наибольшего занятого, начиная с 000001. Для самостоятельных документов источник номера — ID в YAML независимо от имени файла. Для change учитываются также записи с именем `change-NNNNNN` непосредственно в каталогах `changes/` и `archive/changes/` корня документов. Если наибольший занятый номер равен 999999, команда возвращает `E_ID_EXHAUSTED`. Блокирующая ошибка индекса даёт код своей категории (1 для ошибок документов, 2 для незавершённой операции). Подсказки прежних черновиков сами по себе созданию не препятствуют.

Внутри `documents_root` команда создаёт `changes/change-NNNNNN` с `intent.md`, `spec.md` и `plan.md` либо один файл `specs/srs-NNNNNN.md`, `adr/adr-NNNNNN.md` или `research/research-NNNNNN.md`. Она использует актуальные формы установленного пакета, подставляет ID, текущую дату UTC в `created` и `updated` и экранированное для Markdown название. Документы получают `status: draft`, Plan получает `execution: not_started`. При успехе `stdout` содержит ID, относительный путь и состав результата, код завершения 0. Активные подсказки требуют заполнения перед успешным `validate`.

По конечному пути публикуется только полностью записанный файл или комплект. Сбой записи до публикации даёт `E_IO` и код 2. Занятый конечный путь и конфликт между вызовами, выбравшими один ID, дают проигравшему `E_CONFLICT` и код 2 без повторного выбора. Существующие файлы сохраняются. При публикации комплекта внешний процесс может успеть создать пустой каталог по конечному пути между последней проверкой и переименованием. В этом случае каталог может быть заменён. Аварийное прерывание может оставить временные данные вне индексируемых каталогов.

### R-5: Проверка документов

`vf validate` проверяет рабочие и архивные документы подключённого проекта по действующим правилам профиля. Архив входит в индекс. CLI проверяет читаемость и YAML, идентичность, дубликаты, размещение и конечные состояния документов и комплектов, логические адреса и отношения. Для исторических ссылок на требования SRS учитывает ограничения восстановления прежней редакции. В архиве пропускаются проверка полноты актуальной формы и диагностика незаполненных маркеров черновика.

По результатам прохода CLI указывает в `stdout` корень проекта, профиль, число документов, ошибок и предупреждений, охват и ограничения. При пустом индексе отдельно отмечает отсутствие документов. Если проход не состоялся, CLI сообщает корень, невозможность установить профиль, ноль проверенных документов и неполный охват. Диагностики в `stderr` упорядочены по пути, строке, столбцу и коду.

Код 0 означает завершённый проход без ошибок, в том числе с предупреждениями, 1 — ошибки документов, 2 — невозможность завершить проход. При сочетании причин приоритет у 2. `validate` сохраняет файлы, их даты и статусы. Смысловое ревью и проверку поведения выполняют отдельно.

### R-6: Сводка по Journal и stdin

`vf summary change-NNNNNN` читает Journal выбранного рабочего или архивного комплекта, указывает ID и помечает архив. Совпадение ID в обоих местах даёт `E_LOCATION`. Если комплект или его Journal отсутствует, команда возвращает `E_DOCUMENT_NOT_FOUND`. Если в Journal отсутствует список `checks`, команда возвращает `E_FIELD`. В Journal список `checks` берётся из YAML-блока раздела Verification, необязательный `decisions` — из Significant Events. Если несколько YAML-блоков одного раздела задают тот же список, команда возвращает `E_FIELD`. `vf summary --stdin` читает один отчёт YAML или JSON без Markdown и ID, в том числе вне проекта. Вызов `vf summary` без аргументов подсказывает обе формы.

В `stdout` выводятся число проверок, `subject`, `outcome`, `source`, `revision` и `executor` каждой записи в исходном порядке и решения из `decisions` один раз. Для `revision` со значением `null` и для исполнителя, пропущенного или заданного как `null`, выводится пометка о неизвестном значении. При отсутствии решений указывается отсутствие основания согласования. Явный пустой список `checks` даёт ноль проверок.

Полностью выведенная сводка даёт код 0 и при `outcome` со значением `failed`. Пустой `stdin` даёт `E_CLI_COMMAND_USAGE` и код 2. Ошибка чтения или формата, недостающие обязательные поля и дубли ключей дают код 2 и диагностику без частичной сводки. Прежние отчёты без поля `verification` остаются допустимыми. Обе формы сохраняют файлы.

### R-7: Проверка области изменений

`vf scope change-NNNNNN --digest` читает маски рабочей Spec и выводит SHA-256 в нижнем регистре. `vf scope change-NNNNNN` читает рабочий комплект и проверяет изменённые пути Git относительно принятой базы и области. При успехе выводит базу, проверенные слои и число записей путей. Обе формы сохраняют файлы и возвращают 0 при успехе. При отказе код 2, диагностика указывает причину, для запрещённого пути также слой и путь. Основание, вычисление суммы, сопоставление масок и проверяемые слои определяет SRS проверки документов и области изменений.

### R-8: Завершение комплекта

`vf complete change-NNNNNN` проверяет условия допуска рабочего комплекта по SRS проверки документов и области изменений. При успехе переводит `execution` рабочего Plan из `in_progress` в `completed`, сохраняя сторонний текст, и выводит ID и результат с кодом 0. Повтор на уже завершённом рабочем Plan сообщает его состояние с кодом 0 и сохраняет файлы. При отказе команда указывает причину и возвращает 2. Если условия завершения ещё не выполнены, например остался открытый шаг Plan или обязательная проверка не прошла, команда сохраняет Plan и сообщает `E_COMPLETION_BLOCKED`. Для неверного формата поля применяется `E_FIELD`, для повреждённого YAML — `E_YAML`. При обнаружении конкурентной правки Plan команда сообщает `E_CONFLICT`. Ошибка доступа, записи или очистки временного файла даёт `E_IO`. Синхронизацию SRS и архивирование выполняет агент после перехода.

## Verification

Проверить справку и версию из постороннего каталога. Подключить временный проект, повторить команду, вызвать конфликт пути и сравнить байты и время изменения файлов. В установленном tarball проверить доступ к собственным ресурсам, пользовательский текст и полный маршрут `init` → `new` → заполнение → `validate`. Сценарии поставки находятся в [пакетном тесте](../../src/tests/package.integration.ts).

При проверке `init` использовать один блок между строками `<!-- viaferrata:begin -->` и `<!-- viaferrata:end -->`. Проверить новый, изменённый и прежний штатный блоки, ручной текст до и после, BOM и CRLF. Для `.gitignore` проверить новую строку с LF, существующее правило с начальным слешем и без, сохранение дубликатов и отказ при строке с начальным ! после последнего правила. Убедиться, что состояние файлов, которые Git уже отслеживает, сохранилось. При ошибке чтения ресурсов пакета `init` возвращает `E_IO` до записи файлов проекта. Проверить восстановление после частичного сбоя, диагностику конкурентной правки и ошибки очистки временного файла.

Тест поставки устанавливает архив с пустым кешем npm и отключёнными скриптами жизненного цикла пакета. Проверить состав архива. Запустить CLI из постороннего каталога при недоступном каталоге исходников и проверить пути к инструкциям и формам. На независимых заполненных документах ожидать успешный `validate`, на черновиках `new` — диагностику активных маркеров. После теста проверить штатную очистку временного проекта.

Для каждой формы `new` сверить результат с шаблоном установки. Проверить выбор номера с учётом архивных ID и документов прежней формы. При ошибке записи до публикации конечный путь свободен. При конкуренции двух вызовов за один ID виден один полный результат. При ошибке аргументов проверить подсказку команды и сохранность дерева проекта. Для `validate` использовать независимые рабочие и архивные документы. Для `summary` сопоставить записи Journal и `stdin`, в том числе `failed`, пустые списки и повреждённый ввод. Для `scope` проверить сумму и слои Git. Для `complete` сравнить Plan до отказа, после успеха и после повтора.
