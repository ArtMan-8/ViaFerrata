# CLI, skills и агенты

## Контекст

Заметка от 2026-11-14 по обсуждению интерфейса ViaFerrata. Направление требует исследования; будущая архитектура и сроки не утверждены.

### Состояние для выпуска 0.1.0

Для 0.1.0 сохраняется схема: человек общается с агентом, агент читает правила проекта и поставляемые инструкции, затем вызывает CLI по необходимости. Команды `vf init`, `vf new` и `vf validate` доступны как человеку, так и агенту. CLI выполняет заявленные операции и структурные проверки; обращения к модели в нём нет.

Основной пользовательский путь — живая беседа. Пользователь формулирует намерение, агент выбирает необходимые действия в пределах разрешений. Возможность явно вызвать команду сохраняется. Запуск через npx доставляет и запускает CLI; сам по себе он не устанавливает skill и не запускает нейросеть.

При подготовке CHANGELOG команда собирает данные Git, а текущий рабочий агент объясняет пользовательский смысл изменений по diff и документам задач. Отдельный LLM API для этого не нужен.

## Идея

### Возможное развитие

Skills могут соответствовать задачам CLI, но задают инструкции агенту: выяснить параметры, выбрать команду, разобрать результат и продолжить процесс. Skill не обязан повторять CLI один к одному. Например, подключение проекта может включать проверку локальных правил, вызов `vf init` и разбор конфликта. Название `vf:init` обсуждалось как пример, а не как утверждённый синтаксис: способ вызова зависит от агентной среды.

CLI технически может обращаться к модели напрямую или запускать установленный внешний агент. В первом случае потребуются выбор провайдера и модели, настройки соединения и авторизация; для локальной модели ключ может не требоваться. Во втором случае можно использовать собственные настройки и авторизацию агента, если он поддерживает нужный способ запуска. Доступность такого интерфейса следует проверять для конкретного агента.

Секреты не передаются через текст задания или Git. При необходимости используются поддерживаемые окружением переменные или хранилище секретов. Прямой вызов модели и запуск полноценного агента различаются: модель сама по себе не предоставляет исполнение инструментов, управление разрешениями и сохранение состояния.

### Возможная команда обнаружения задач

Дополнение от 2026-11-15: рассмотреть `vf list` с фильтром по `execution` и выводом ID, названия и пути к Plan. Команда могла бы заменить ручной поиск агентом по метаданным в `documents_root`, не создавая отдельного указателя текущей задачи. Сейчас такой команды нет; название, синтаксис и состав вывода не утверждены.

Перед реализацией определить поведение при нескольких кандидатах, отсутствии задач и ошибках метаданных. Список не должен автоматически выбирать задачу, менять документы или разрешать продолжение работы. До отдельного согласования достаточно правила поиска в общих инструкциях; команда не входит в текущую реализацию выпуска.

### Подключение проекта и создание документов

В [quickstart](../../docs/quickstart.md#подключение-проекта) показано, как при первом подключении вызвать `vf init`, выбрать профиль и корень документов и проверить результат. При повторе то же руководство объясняет сохранение файлов. [Инструкция агенту](../../instructions/workflow.md#подключение-проекта) задаёт порядок действий при конфликте пути или ручной правке блока. Из README доступна [SRS «CLI-инструменты»](../specs/srs-000003-cli-tools.md) с действующим синтаксисом `vf new`.

В [руководстве по началу работы](../../docs/quickstart.md#от-цели-до-проверки) приведены примеры выбора типа. По выводу команды человек находит каталог комплекта change или файл самостоятельного документа.

По [инструкции подготовки документов](../../instructions/workflow.md#режим-и-документы-задачи) агент заполняет три черновика change и предъявляет их для согласования. Journal появляется с началом реализации. Для требований существующей области агент готовит дельту к действующей SRS. Для новой области он создаёт SRS, добавляет к ID в имени файла краткое название, заполняет документ и согласует требования с человеком. [Журнал проверки этих сценариев](../archive/changes/change-000014/journal.md#verification) описывает фактические действия и ограничения проверки.

## Что выяснить

Вопросы отложены для исследования после 0.1.0:

- Какие задачи достаточно описать в AGENTS и общих инструкциях, а какие выигрывают от отдельных skills?
- Где полезно соответствие имён CLI и skills, а где skill должен объединять несколько действий? Как это переносится между агентными средами?
- Как агент выбирает действие в беседе, сообщает о существенном выборе и сохраняет возможность явного управления пользователем?
- Нужен ли вызов модели из CLI для конкретного сценария? Сравнить текущего агента, внешний агентный CLI и прямой API по сложности, стоимости, переносимости и контролю действий.
- Как устроены авторизация, отмена, ошибки, ограничения времени и затрат, потоковый вывод и продолжение после прерывания?
- Как избежать рекурсивной цепочки «агент → vf → агент → vf», дублирования контекста и неявного расширения полномочий?
- Как проверять поведение skills и беседы отдельно от тестов CLI? Как обновлять интеграцию, сохраняя пользовательские инструкции?

Эта заметка не добавляет отдельные skills, агентный runtime, LLM API или новые команды в scope первого выпуска. Перед реализацией необходимы исследование конкретного сценария и согласование содержательной дельты. Заметка относится к документации репозитория; включать её в npm-пакет не требуется.
