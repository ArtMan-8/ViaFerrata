# Публичный интерфейс `vf` и корень документов при подключении

## Change Boundaries

Новая SRS «CLI-инструменты» получает свободный ID srs-000003 и файл cli-tools.md. Её R-1–R-8 задают синтаксис и наблюдаемые результаты. В origin новой SRS включить источники, перечисленные в origin этой Spec, и change-000013/spec для нового поведения. Типизированный `new` относится к следующему change.

В srs-000001 R-1 сохраняет конфигурацию правил, R-2 и R-7 — покрытие, R-3, R-5 и R-6 — идентичность и диагностику правил, R-4 — каталог и навигацию. Добавить навигацию к CLI-SRS. Специальные тесты бывшего ключа конфигурации удалить, общую проверку неизвестного ключа сохранить. В srs-000002 уточнить R-1, R-3, R-6 и R-8 с сохранением ID. R-2, R-4–R-5 и R-7 и R-9–R-10 сохраняют семантику области, отношений и допуска. Добавить взаимные ссылки между владельцами.

## Requirements

### R-1: Вызовы, справка и версия

```yaml
operation: add
changes: srs-000003/R-1
after: |-
  В поддерживаемой среде Node.js 24.x вызовы `vf` и `vf --help` выводят справку со всеми командами и абсолютными путями к `instructions/workflow.md` и `templates/README.md` из запущенной установки. `vf --version` выводит версию установленного пакета. Для этих вызовов конфигурация не требуется, файлы сохраняются, код успеха 0. Опции `--help` и `--version` используются самостоятельно. При неизвестной опции CLI выводит в `stderr` общую диагностику `E_USAGE` с подсказкой «см. `vf --help`», возвращает 2 и сохраняет файлы. Неверная команда, повтор опции или лишний аргумент также дают `E_USAGE` и код 2. Неподдерживаемая версия запущенного Node даёт `E_RUNTIME` и код 2.

  Команды `new`, `validate`, `summary` по ID, `scope` и `complete` выбирают ближайший `viaferrata.toml` вверх от `cwd`. Отсутствие проекта или ошибка найденной конфигурации останавливают команду с кодом 2. Диагностика в `stderr` указывает место, код, причину и способ исправления. Для нарушенного встроенного правила указывается публичный ID по каталогу встроенных проверок.
```

### R-2: Выбор каталога и конфигурации `init`

```yaml
operation: add
changes: srs-000003/R-2
after: |-
  `vf init [path] [--profile lite|strict] [--documents-root <path>]` подключает существующий каталог `path` относительно `cwd` либо сам `cwd`. Корень Git автоматически не определяется. Обе опции принадлежат только `init`, допускаются по одному разу до или после команды, со значением через пробел или знак равенства.

  Первое подключение внутри уже подключённого проекта запрещено. Для создания TOML требуется явный профиль. Если профиль пропущен, CLI до записи возвращает `E_CONFIG` и код 2. В `stderr` он кратко объясняет выбор: `lite` включает базовые проверки документов, `strict` дополнительно проверяет покрытие требований шагами Plan и критериев приёмки записями Journal в deep-задачах. Подсказка даёт оба вызова с `--profile`.

  При повторном `vf init` без опций используется профиль существующего TOML. При создании конфигурации без `--documents-root` в TOML записывается только строка `profile` с LF. Корень документов по умолчанию — `viaferrata/`. Если при создании конфигурации задан `--documents-root`, команда записывает значение аргумента в строковое поле `documents_root`. При чтении TOML сохраняются все символы исходного пути, включая пробелы и кавычки.

  К аргументу применяются правила `documents_root` каталога встроенных проверок и проверка совместимости пути с файлами подключения. Корень отсчитывается от проекта. При существующем TOML используются его настройки. Явный профиль должен совпадать. После проверки исходного аргумента корни сравниваются как пути с нормализованными разделителями. Иное написание того же пути сохраняет исходный TOML. Несовпадающий профиль или корень и недопустимое значение пути дают `E_CONFIG` до записи, отсутствие значения опции даёт `E_USAGE`. `init` сохраняет существующие документы на месте.
```

### R-3: Файлы подключения и восстановление

```yaml
operation: add
changes: srs-000003/R-3
after: |-
  `init` создаёт или дополняет только `viaferrata.toml`, `AGENTS.md` и `.gitignore`. В `AGENTS.md` добавляется один штатный блок навигации к инструкциям выбранной установки. Блок указывает, как найти `workflow.md` через справку выбранной установки. Ручной текст вне блока сохраняется, сравнение штатного тела допускает LF и CRLF. Ранее поставленные штатные блоки принимаются. Изменённый, непарный, переставленный или повторённый маркер требует разрешения конфликта. Для временного каталога добавляется строка `/.viaferrata/`. Самостоятельная строка с начальным слешем или без него достаточна. Более позднее отрицание требует ручной проверки. При добавлении исходные байты сохраняются префиксом с подходящим разделителем строк.

  Неподдерживаемая кодировка дополняемого файла даёт `E_UNSUPPORTED`. `init` сохраняет BOM, существующие переводы строк и права дополняемого файла. До первой записи `init` проверяет конфигурацию, доступность ресурсов пакета, типы путей и все три файла подключения. Симлинк даёт `E_UNSUPPORTED`, несовместимый тип файла подключения или конфликт блока дают `E_EXISTS`. Пересечение корня документов с файлом подключения и файл на месте каталога документов дают `E_CONFIG`. Проверяемый конфликт сохраняет состояние проекта. Перед записью проверяется конкурентное изменение. Изменения применяются в порядке `.gitignore`, `AGENTS.md`, новая конфигурация. При обработанном сбое временные файлы операции очищаются, ошибка очистки диагностируется. При сбое записи CLI указывает проблемный путь, уже выполненные изменения и способ продолжения. После исправления причины повтор дополняет недостающее. Готовые файлы сохраняют байты и `mtime`.

  При успехе, в том числе при повторе, код 0. В `stdout` выводятся абсолютные корни проекта и документов, профиль, действие для каждого файла, пути к инструкциям и руководству форм. Подсказка предлагает открыть проект с агентом, назвать цель задачи и ожидаемый результат. При отказе код 2, причина в `stderr`.
```

### R-4: Создание комплекта

```yaml
operation: add
changes: srs-000003/R-4
after: |-
  `vf new "Название задачи"` принимает одно непустое однострочное название. Название используется в заголовках документов с экранированием Markdown. Команда выбирает следующий шестизначный номер после наибольшего занятого в рабочих и архивных комплектах. Она создаёт внутри `documents_root/changes` каталог `change-NNNNNN` и ровно три файла из форм установленного пакета: `intent.md`, `spec.md` и `plan.md`. Статусы `draft`, `execution` плана `not_started`, даты создания и обновления соответствуют текущей дате UTC. В `stdout` выводятся ID, относительный путь и состав черновика. Код успеха 0. Название с префиксом `--` отклоняется с `E_USAGE`. Активные подсказки требуют заполнения перед успешным `validate`.

  Ошибка индекса, препятствующая созданию, возвращает код по категории диагностики (1 для ошибок документов, 2 для незавершённой операции). Исчерпание номеров, конфликт создания и сбой записи дают код 2. Команда сохраняет существующие файлы, сообщает созданные пути при частичном сбое и учитывает занятый номер при следующем запуске.
```

### R-5: Проверка документов

```yaml
operation: add
changes: srs-000003/R-5
after: |-
  `vf validate` проверяет рабочие и архивные документы подключённого проекта по действующим правилам профиля. Архив входит в индекс. CLI проверяет читаемость и YAML, идентичность, дубликаты, размещение и конечные состояния документов и комплектов, логические адреса и отношения. Для исторических ссылок на требования SRS учитывает ограничения восстановления прежней редакции. В архиве пропускаются проверка полноты актуальной формы и диагностика незаполненных маркеров черновика.

  По результатам прохода CLI указывает в `stdout` корень проекта, профиль, число документов, ошибок и предупреждений, охват и ограничения. При пустом индексе отдельно отмечает отсутствие документов. Если проход не состоялся, CLI сообщает корень, невозможность установить профиль, ноль проверенных документов и неполный охват. Диагностики в `stderr` упорядочены по пути, строке, столбцу и коду.

  Код 0 означает завершённый проход без ошибок, в том числе с предупреждениями, 1 — ошибки документов, 2 — невозможность завершить проход. При сочетании причин приоритет у 2. `validate` сохраняет файлы, их даты и статусы. Смысловое ревью и проверку поведения выполняют отдельно.
```

### R-6: Сводка по Journal и `stdin`

```yaml
operation: add
changes: srs-000003/R-6
after: |-
  `vf summary change-NNNNNN` читает Journal выбранного рабочего или архивного комплекта, указывает ID и помечает архив. Совпадение ID в обоих местах, отсутствие комплекта или списка `checks` дают отказ. В Journal список `checks` берётся из YAML-блока раздела Verification, необязательный `decisions` — из Significant Events. Повтор списка в его разделе неоднозначен. `vf summary --stdin` читает один отчёт YAML или JSON без Markdown и ID, в том числе вне проекта. Вызов `vf summary` без аргументов подсказывает обе формы.

  В `stdout` выводятся число проверок, `subject`, `outcome`, `source`, `revision` и `executor` каждой записи в исходном порядке и решения из `decisions` один раз. Для `revision` со значением `null` и для исполнителя, пропущенного или заданного как `null`, выводится пометка о неизвестном значении. При отсутствии решений указывается отсутствие основания согласования. Явный пустой список `checks` даёт ноль проверок.

  Полностью выведенная сводка даёт код 0 и при `outcome` со значением `failed`. Пустой `stdin`, ошибка чтения или формата, недостающие обязательные поля и дубли ключей дают код 2 и диагностику без частичной сводки. Прежние отчёты без поля `verification` остаются допустимыми. Обе формы сохраняют файлы.
```

### R-7: Проверка области изменений

```yaml
operation: add
changes: srs-000003/R-7
after: |-
  `vf scope change-NNNNNN --digest` читает маски рабочей Spec и выводит SHA-256 в нижнем регистре. `vf scope change-NNNNNN` читает рабочий комплект и проверяет изменённые пути Git относительно принятой базы и области. При успехе выводит базу, проверенные слои и число записей путей. Обе формы сохраняют файлы и возвращают 0 при успехе. При отказе код 2, диагностика указывает причину, для запрещённого пути также слой и путь. Основание, вычисление суммы, сопоставление масок и проверяемые слои определяет SRS проверки документов и области изменений.
```

### R-8: Завершение комплекта

```yaml
operation: add
changes: srs-000003/R-8
after: |-
  `vf complete change-NNNNNN` проверяет условия допуска рабочего комплекта по SRS проверки документов и области изменений. При успехе переводит `execution` рабочего Plan из `in_progress` в `completed`, сохраняя сторонний текст, и выводит ID и результат с кодом 0. Повтор на уже завершённом рабочем Plan сообщает его состояние с кодом 0 и сохраняет файлы. При отказе команда указывает нарушенное условие, сохраняет Plan и возвращает 2. Синхронизацию SRS и архивирование выполняет агент после перехода.
```

### R-9: Основание и вычисление суммы

```yaml
operation: modify
changes: srs-000002/R-1
before: |-
  При создании Spec и после каждой дельты агент записывает scope в порядке дерева проекта. CLI использует тот же порядок для вычисления суммы. Перестановка строк сохраняет сумму.
  Команда vf scope change-NNNNNN --digest выводит SHA-256 принятого к рассмотрению списка масок рабочей Spec без записи в файлы. Команда vf scope change-NNNNNN проверяет изменения по этой Spec и записи в Journal. В Significant Events агент хранит YAML-блок scope_check с полями base (полный SHA исходного коммита) и digest (SHA-256 текущего принятого scope). В decisions агент записывает основание согласования.   Для суммы CLI сортирует копию масок в порядке дерева, сериализует её через `JSON.stringify` без пробелов и вычисляет SHA-256 байтов UTF-8. Отсутствие `scope` соответствует пустому списку. В Significant Events агент хранит YAML-блок `scope_check` с полями `base` (полный SHA исходного коммита) и `digest` (SHA-256 текущего принятого `scope`). В `decisions` агент записывает основание согласования. После принятой дельты агент описывает точное изменение прав и обновляет `digest`, сохраняя `base`. Одного изменения Spec недостаточно. CLI проверяет совпадение суммы; авторство решения и подлинность Journal устанавливает человек или агент.
```
