# Встроенные правила ViaFerrata

## Change Boundaries

Первое расширение core для deep-комплектов проверяет структурное покрытие. Полная матрица отношений, проверка diff по scope и автоматизация завершения остаются отдельными задачами.

## Requirements

### R-1: Выбор профиля и дополнительных правил

- Operation: modify
- Changes:
  - [srs-000001/R-1]
- Before: CLI принимает отсутствие `required_checks` или пустой массив `required_checks = []` в `viaferrata.toml`. Значение должно быть массивом непустых строк; неверный тип или пустая либо состоящая только из пробелов строка дают `E_CONFIG`. Непустой массив даёт `E_UNSUPPORTED`: исполнение обязательных проверок этой настройкой не поддерживается. Ключ `checks`, включая форму `[[checks]]`, даёт `E_CONFIG` как неизвестный ключ. Эти правила действуют при чтении конфигурации командами init, new и validate.

  Отклонение конфигурации не разрешает удалять обязательства ради успешного запуска CLI. Применимые проверки проекта агент выполняет самостоятельно; успешный validate не подтверждает выполнение этих проверок, достоверность evidence или завершение задачи.

- After: CLI принимает required_checks как список ID дополнительных встроенных правил. Отсутствующее поле и пустой список оставляют профиль без дополнений. Базовые проверки конфигурации, структуры, идентичности и ссылок действуют в обоих профилях. Правило plan-requirement-coverage входит в strict и может быть включено в lite. Неизвестный ID или неверный тип даёт E_CONFIG; повторный выбор одного правила оставляет его включённым однократно. Команды init, new и validate используют общую конфигурацию. Поведение protected_paths сохраняется.

### R-2: Покрытие рабочей Spec

- Operation: add
- Changes:
  - [srs-000001/R-2]
- After: При включённом plan-requirement-coverage команда validate проверяет каждый объявленный R рабочей Spec. В том же deep-комплекте у шага P должна быть явная связь Covers на этот R либо на AC Intent, у которого есть Covers на этот R. Отсутствие покрытия даёт E_PLAN_COVERAGE с адресом требования и ненулевой код завершения. Примеры кода, текстовые упоминания и связи другого change покрытия не дают. В архиве правило не применяется. В vibe отсутствие комплекта допустимо. Покрытие описывает план работ; проверку поведения выполняет агент или CI средствами проекта.

### R-3: Публичный ID в диагностике

- Operation: add
- Changes:
  - [srs-000001/R-3]
- After: Каждое самостоятельное проверяемое условие встроенной валидации имеет публичный ID. При нарушении правила CLI выводит его ID вместе с существующим кодом диагностики. Для одного нарушения конфигурации init, new и validate выводят один и тот же ID. Ошибки ввода-вывода и другие сбои выполнения сохраняют собственную диагностику. Уровни сообщений, коды завершения, условия применения правил и допустимые значения TOML сохраняются.

### R-4: Каталог встроенных правил

- Operation: add
- Changes:
  - [srs-000001/R-4]
- After: SRS встроенных проверок содержит таблицы по областям. Каждому публичному ID соответствует одна строка с проверяемым условием, областью применения, порядком включения в профилях и кодами диагностики. Для рабочих и архивных документов каталог указывает применимые различия. README и руководство быстрого старта ведут к каталогу.

### R-5: Область применения публичных правил

- Operation: add
- Changes:
  - [srs-000001/R-5]
- After: CLI выводит действующие ID из каталога. Для полей scope и списков ссылок действуют разные правила. Режим выполнения волны и наличие шагов проверяются независимо. Для комплекта с архивными документами целостность переноса и конечное состояние Plan также проверяются независимо. При нарушении обоих условий CLI выдаёт обе диагностики. Правила размещения локальных объявлений и обязательных разделов учитывают частные случаи Journal и ADR. Текст сообщения указывает конкретный подраздел или нарушенное условие.

#### Переход с ID второго этапа

| Прежний ID              | Действующий ID                                        | Условие                                                                     |
| ----------------------- | ----------------------------------------------------- | --------------------------------------------------------------------------- |
| `metadata-list`         | `scope-list`, `reference-list`                        | Форма списка scope или списка ссылок в YAML соответственно.                 |
| `wave-contents`         | `wave-execution`, `wave-steps`                        | Ровно одно допустимое Execution и хотя бы один шаг в волне.                 |
| `archive-change-state`  | `archive-change-location`, `archive-change-execution` | Полный перенос комплекта и конечное execution у Plan.                       |
| `verification-location` | `local-declaration-location`                          | Запись V находится в подразделе Verification.                               |
| `adr-outcome-sections`  | `required-sections`                                   | Подразделы Consequences и Confirmation расположены внутри Decision Outcome. |

CLI и текущий каталог переходят сразу на целевые ID. Коды и уровни диагностик, коды завершения и семантика required_checks сохраняются.

### R-6: Код диагностики встроенного правила

- Operation: add
- Changes:
  - [srs-000001/R-6]
- After: Определение каждого встроенного правила связывает его публичный ID с одним итоговым кодом диагностики. При нарушении правила CLI берёт ID и код из определения. Сообщение поясняет конкретное нарушение. Расположение документа определяет применимость проверки формы.

## Definition of Done

Проверить штатные команды и установку пакета. Удалить отвергнутые определения внешних команд и снимки. Синхронизировать SRS и архивировать комплект после успешных проверок.
