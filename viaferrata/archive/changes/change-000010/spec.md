# Контроль diff и согласованного scope

## Change Boundaries

Ввести проверку для указанного рабочего deep-комплекта в обоих профилях. Сохранить самостоятельный вызов `vf validate`. Новая SRS проверки документов и завершения (`srs-000002`) описывает границы структурной проверки со ссылкой на действующий каталог и контракт контроля scope. Автоматический допуск к completed, hooks и атрибуция изменений остаются за пределами этого change.

## Requirements

### R-1: Основание проверки

```yaml
operation: add
changes: srs-000002/R-1
after: |-
  При создании Spec и после каждой дельты агент записывает scope в порядке дерева проекта. CLI использует тот же порядок для вычисления суммы. Перестановка строк сохраняет сумму.
  Команда vf scope change-NNNNNN --digest выводит SHA-256 принятого к рассмотрению списка масок рабочей Spec без записи в файлы. Команда vf scope change-NNNNNN проверяет изменения по этой Spec и записи в Journal. В Significant Events агент хранит YAML-блок scope_check с полями base (полный SHA исходного коммита) и digest (SHA-256 текущего принятого scope). В decisions агент записывает основание согласования. После принятой дельты агент описывает точное изменение прав и обновляет digest, сохраняя base. Одного изменения Spec недостаточно. CLI проверяет совпадение суммы; авторство решения и подлинность Journal устанавливает человек или агент.
```

Порядок определяется по компонентам пути, без обращения к файловой системе. На каждом уровне сначала идут каталоги с содержимым, затем файлы. В каждой группе имена сравниваются по байтам UTF-8 после приведения к нижнему регистру без учёта локали. При равенстве сравниваются байты исходных имён. Например, `src/cli/*` предшествует `src/config.ts`, а корневой `README.md` идёт после ветки `src/`.

Для вычисления SHA-256 CLI сортирует копию списка по этому правилу, сериализует её через JSON.stringify без пробелов и кодирует результат в UTF-8. Сумма записывается строчными шестнадцатеричными цифрами. Отсутствующее поле соответствует пустому массиву. Команда --digest работает до создания Journal. Для проверки нужны однозначная запись scope_check, непустой список decisions и доступный коммит-предок HEAD (включая сам HEAD). При отсутствии основания, расхождении суммы или недоступной базе команда возвращает ненулевой код и сообщает способ продолжения. Обновлять digest можно после проверки и записи решения пользователя.

### R-2: Область разрешённых путей

```yaml
operation: add
changes: srs-000002/R-2
after: |-
  Путь задаётся относительно корня проекта с разделителем / и сравнивается с учётом регистра. Звёздочка соответствует любой последовательности символов внутри одного компонента, включая точку. Конечное /** разрешает файлы на любой глубине внутри указанной директории. Точный путь разрешает только этот файл. Автоматически разрешены только Intent, Spec, Plan и Journal выбранного change. Эти правила действуют и для новых путей.
```

Маски с абсолютным путём, пустыми компонентами, компонентами . или .., обратной косой чертой и неподдерживаемым glob-синтаксисом отклоняются с указанием маски. В инструкции и шаблоне показать выбор между модулем с одноимённым тестом (`path/func.*`), каталогом (`path/*`), поддеревом и конкретными файлами на примере изменения общего компонента.

### R-3: Проверяемые изменения Git

```yaml
operation: add
changes: srs-000002/R-3
after: |-
  Команда проверяет объединение путей разности деревьев base и HEAD, изменений индекса относительно HEAD, рабочего дерева относительно индекса и неигнорируемых untracked-файлов. Проверяются удалённые пути и обе стороны переноса. Изменения разных слоёв не погашают друг друга. При нарушении команда называет путь, слой и способ продолжения и возвращает ненулевой код. Код 0 означает, что все заявленные слои прочитаны и все обнаруженные пути разрешены.
```

Первый срез поддерживает проект в корне рабочего дерева Git. Для вложенного проекта, конфликта индекса, изменённой записи подмодуля, симлинка среди изменений или иного неподдерживаемого объекта команда сообщает ограничение и завершает проверку с ошибкой. Ссылку проверяют по типу записи без обхода её цели. Игнорируемые untracked-файлы исключены, tracked-файлы проверяются независимо от ignore. Итог описывает пути на момент проверки; успешный результат не удостоверяет совпадение содержимого индекса и рабочего дерева.

Базовые проверки конфигурации, структуры, идентичности и ссылок действуют в обоих профилях. Правило plan-requirement-coverage входит в strict и может быть включено в lite. Неизвестный ID или неверный тип даёт E_CONFIG; повторный выбор одного правила оставляет его включённым однократно. Команды init, new и validate используют общую конфигурацию. Поведение protected_paths сохраняется.
after: |-

## Definition of Done

Проверить сценарии Intent через публичный CLI, оба профиля и установку архива. Проверить выбор маски на семействе файлов и на соседнем модуле. Синхронизировать принятые дельты SRS и актуальные инструкции по правилам проекта.
