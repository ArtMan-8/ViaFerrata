# SRS функциональных областей и архивирование изменений

## Change Boundaries

Изменение определяет содержание SRS функциональной области, дельты требований и процедуру синхронизации с архивированием. Обновляются формы, инструкции и объяснения; CLI получает поддержку архивного размещения, дельт и соответствующих диагностик.

Агент применяет принятую дельту и переносит документы. CLI индексирует действующие и архивные документы, проверяет целостность, различает назначения ссылок и сообщает о незавершённой процедуре. Полная матрица отношений и структурное покрытие относятся к M23-7, общий допуск к завершению — к M23-8. Сценарии этого change служат входом сквозной проверки M23-9.

## Requirements

### R-1: Контекст функциональной области

SRS хранит актуальные принятые требования связной области поведения и контекст, необходимый для их понимания. Одна SRS развивается через несколько changes; один change может затронуть несколько SRS. Начальная спецификация может описывать только реализуемую часть области.

Обязательные H2:

- Purpose and Boundaries — назначение, пользователи, ответственность и исключения.
- System Overview — связное объяснение понятий, ролей, состояний и внешних взаимодействий по применимости.
- Requirements — проверяемые обязательства с объявлениями R-N на H3.
- Verification — устойчивые способы проверки требований, сценарии и ссылки на проверки. Один способ может покрывать несколько R.

Scenarios и приложения добавляются по необходимости. При подготовке требований рассматриваются поведение, интерфейсы, данные, состояния, ошибки, граничные случаи, инварианты, совместимость, качества и существенные ограничения. Это подсказки анализа полноты: неприменимые подразделы убираются, существенные неизвестные вопросы остаются явными. Небольшая область может быть описана несколькими абзацами и требованиями.

SRS содержит действующие обязательства; архитектурное описание — устройство, ADR — существенные решения и основания, Journal/evidence — факты исполнения и результаты проверок.

### R-2: Явная дельта

В change/spec дельта к SRS описывается внутри R: Operation со значением add, modify или remove; Changes с полным адресом R SRS; Before для modify/remove и After для add/modify. Before и After содержат полный нормативный текст соответствующей редакции, включая существенные условия и ограничения. Дельта определяется до исполнения и уточняется вместе с задачей.

При modify сохраняется ID требования; самостоятельное новое обязательство получает новый ID. При remove отменяется обязанность поддерживать поведение; запрет этого поведения задаётся отдельным требованием. ID требований не переиспользуются, включая отменённые. Номера удалённых неначатых changes могут использоваться повторно по R-5.

Если задача создаёт новую SRS, Spec заранее задаёт назначение области, границы и будущие ID SRS/R. Отсутствие адресата допустимо для планируемой операции add; обычная ссылка на отсутствующую цель остаётся ошибкой. Перед применением modify/remove сверяется исходный текст; расхождение требует разрешения конфликта.

Change может задавать собственные требования без связи с SRS. Позднее первоначальная SRS может быть подготовлена из нескольких принятых changes со сверкой последующих изменений, реализации и проверок. Происхождение сохраняется в новой SRS.

### R-3: Синхронизация и архивирование

Последовательность работы: реализация и её проверки → execution completed → сверка и применение дельты к SRS → проверка постоянных документов → немедленное архивирование комплекта. До применения SRS хранит предыдущий принятый контракт, Spec — согласованное изменение; при исполнении учитываются оба документа. В SRS переносится результирующее требование вместе с затронутым контекстом и Verification.

Синхронизация и перенос составляют одну процедуру. Если комплект с `execution: completed` и применимой дельтой остаётся вне архива, процедура ещё не завершена. CLI выводит предупреждение о необходимости её завершить; оно не утверждает, что SRS ещё не изменена. При восстановлении контекста агент учитывает такие changes вместе с постоянными документами.

При прерывании агент восстанавливает ход процедуры по фактическому расположению документов и состоянию SRS. При продолжении сверяет Before/After с текущим состоянием, определяет уже выполненные действия и завершает оставшиеся проверки и перенос. Частичное применение и изменения от других задач требуют явной сверки; повторное применение дельты вслепую недопустимо. Процедура не гарантирует атомарности записи нескольких файлов.

Обнаруженная необходимость доработать реализацию или её проверки возвращает исполнение change в работу. Уточнение целевых обязательств требует согласования дельты.

Change без связи с SRS не обязан синхронизироваться или архивироваться; отсутствие SRS само по себе не вызывает предупреждение. Если реализация не начиналась, ненужный черновой комплект можно удалить без создания дополнительных артефактов; перед удалением проверяются входящие ссылки. Отменённый change не применяет непринятую дельту. Перед архивированием частично исполненной отменённой задачи определяется судьба результата: откат либо явно принятая сохраняемая часть.

### R-4: Архив и конечные состояния

Пути архива отсчитываются от `documents_root`:

- `archive/changes/change-NNNNNN/` — полный комплект change.
- `archive/specs/` — выбывшие SRS.
- `archive/adr/` — выбывшие ADR.
- `archive/research/` — выбывшие исследования.

Расположение определяет архивность. Status сохраняет смысл состояния документа, execution Plan — исполнения задачи. Архивирование допускается для changes с execution completed/cancelled; для SRS/ADR — status cancelled/superseded; для Research — completed/cancelled/superseded при установленной потере дальнейшей применимости. Возраст и завершённость исследования сами по себе не требуют переноса.

Документ сохраняет ID и смысловое имя, change переносится комплектом. Один ID существует в одном месте. Архивируются выбывшие документы; история редакций сохраняется в Git. Обычное изменение требования обновляет существующую SRS. При замене целой SRS применяется `supersedes` того же типа. При отмене последнего требования области последняя содержательная SRS переносится в архив с cancelled, а отмена фиксируется в change.

Синхронизация и архивирование не изменяют содержание завершённого change и не добавляют записи в Journal: архивность определяется расположением. Допустимо исправить относительные файловые ссылки, нарушенные перемещением. Основание выбытия самостоятельного документа задаётся в сопровождающем change до завершения либо в самом документе.

### R-5: Обнаружение и сохранность

Обычное обнаружение задач и действующих требований исключает архив. Чтобы выяснить причину изменения, найти прежнюю договорённость или разобраться в регрессии, агент обращается к истории конкретного изменения.

CLI индексирует рабочие и архивные документы для разрешения ссылок и глобальной уникальности ID. New выбирает следующий номер по существующим рабочим и архивным документам и занятым именам, включая неполные комплекты. Удалённые неначатые changes не резервируют номер; история Git не исследуется. Проверяется соответствие пути типу и ID документа, а архивного размещения — допустимому конечному состоянию.

При переносе сохраняются необходимые материалы, проверяются входящие и относительные файловые ссылки. Занятый путь назначения не перезаписывается. Незавершённый перенос восстанавливается по фактическому состоянию; одно наличие архивного каталога не доказывает корректного завершения процедуры.

### R-6: Исторические ссылки

Changes связывает дельту с идентичностью требования; Before/After фиксирует текст перехода. ID текущего R сам по себе не обозначает его прежнюю редакцию. Исторический результат проверки не подтверждает более позднее требование. Для новых AC и Verifies change предпочтительны ссылки на собственные R Spec, фиксирующие проверяемое изменение; прямые ссылки на SRS допустимы по смыслу.

Ссылки на целый архивный документ разрешаются общим индексом. Содержательная зависимость из текущего документа от архивного вызывает предупреждение с указанием источника, адресата и назначения связи. Origin и `supersedes` допустимы как явное происхождение. Архивирование разрешено до исправления всех входящих зависимостей; дальнейшее изменение источников выполняется по потребности.

Историческое обращение к удалённому R может разрешаться через сохранённую дельту отмены. Если редакцию восстановить нельзя, диагностика сообщает об ограничении, не подставляя произвольный текст. Для восстановления конкретной редакции документа используется Git. Отменённые R удаляются из актуальной SRS; их содержание сохраняется в дельтах и истории.

Обычная текущая ссылка на отсутствующее R или документ остаётся ошибкой. Старые ссылки не переписываются автоматически. Проверка различает историческую идентичность требования и доказанность его редакции на момент события.

### R-7: Актуальная форма и границы проверки

Поставляются актуальные шаблоны и правила их проверки. Неархивные документы сравниваются с текущей формой; отсутствующие разделы и другие несоответствия формы дают предупреждения без автоматической перезаписи. Одинаковые несоответствия получают одинаковую диагностику независимо от возраста документа. Предупреждение не освобождает агента от требований подготовки и проверки текущей задачи. Активный маркер `TODO(VF)` вне архива означает незаполненное содержание и остаётся ошибкой `E_DRAFT_PLACEHOLDER`; в архиве эта проверка не выполняется.

Архивные документы сохраняются без приведения к текущей форме и без проверки её полноты. CLI читает необходимый минимум для определения ID, типа, конечного состояния, адресуемых элементов и связей. Нечитаемые файлы или YAML, невозможность определить ID/тип, дубликаты ID, недопустимое расположение, нарушение конечных состояний и повреждённые текущие ссылки остаются ошибками целостности.

Отчёт явно различает ошибки, предупреждения и неполный охват. Индексация архива не выдаётся за проверку его соответствия актуальным шаблонам; структурная проверка не доказывает согласование, смысловую полноту и корректность реализации.

Правила подготовки дельты, обновления SRS и синхронизации с архивированием доступны по маршрутам workflow. Формы и отношения определяются руководством шаблонов; реализация — инструкцией implementation, синхронизация, отмена и архивирование — инструкцией sync-and-archive; факты исполнения — правилами Journal; содержательная сверка — инструкцией проверки артефактов.

## Scenarios

Ожидания заданы до реализации и прогонов. Примеры используют вымышленную область экспорта; SRS продукта не создаются.

### S-1: Новая область

До первого change SRS нет. После принятого добавления она объясняет область экспорта и содержит первое R о CSV с заголовком. Дельта заранее задаёт область, ID и полный текст; до создания цели нет ложной логической ссылки.

### S-2: Следующее изменение

Второй change меняет разделитель CSV с запятой на точку с запятой, сохраняя ID. Постоянная SRS отражает новое обязательство, дельта сохраняет прежнее и новое; архив не нужен для понимания актуального формата. Отдельное новое R об экспорте JSON получает следующий свободный ID.

### S-3: Отмена обязанности

Третий change отменяет обязанность поддерживать CSV, оставляя JSON. R CSV удалено из актуальной SRS, ID не переиспользован, запрет CSV не придуман. Для отмены последнего оставшегося R проверить вывод всей области: последняя содержательная SRS становится cancelled и переносится в `archive/specs`; в активном specs пустого документа нет.

### S-4: Архивирование и прерывание

Completed ещё не означает завершённой процедуры синхронизации и архивирования. Проверить completed → применение → немедленный перенос, частичное применение и сбой после записи SRS до переноса. Для неархивного completed с дельтой выдаётся предупреждение о незавершённой процедуре; повтор восстанавливает её без двойного применения и не утверждает, что вне архива SRS обязательно не изменена. После сверки результата комплект переносится без содержательных изменений и записи об архивировании в Journal, ID и ссылки сохраняются; обычное обнаружение исключает archive. Занятый путь назначения и прерванный перенос не дают ложного archived и не приводят к перезаписи истории.

### S-5: Отменённый change

Предложение вернуть CSV отменено: execution cancelled, новый контракт не применён. Вторая вариация — часть работы уже выполнена: без решения о судьбе остатка архивирование не завершается. При отмене до Implement черновой комплект удаляется без Journal и дополнительных записей; текущие входящие ссылки не должны оставаться повреждёнными. Освободившийся номер может использоваться повторно.

### S-6: Историческая ссылка

Из архивной дельты восстанавливаются прежний текст R и причина изменения/отмены. Новая форма исторического соответствия проверяется CLI в принятом объёме и агентом по смыслу. Отдельно проверить старую ссылку без сохранённой редакции. CLI сообщает, что установить редакцию нельзя. Подставлять произвольный текст запрещено. Ожидаемые диагностики фиксируются до прогона.

### S-7: Восстановление контекста

Отдельный агент получает только постоянную SRS после S-3, применимые инструкции и новую задачу изменить JSON. Он называет актуальное R JSON, не считает CSV обязательным или запрещённым, определяет затронутое требование и не обращается к архиву. Ему не передают ожидаемый ответ или историю прогонов. Маленькая SRS не содержит пустых подразделов, обязательной таблицы неприменимости или текущих результатов проверок.

### S-8: Маршрутизация и CLI

Из workflow находятся правила подготовки дельты, обновления SRS, завершения и архивирования. Сначала подтвердить текущие ограничения, затем проверить поддержку принятого archive/, уникальность ID между рабочими и архивными документами, выделение следующего номера и исторические ссылки. Проверить cancelled/superseded SRS и ADR, completed Research с явным основанием архивации, несовместимые состояния и дубликаты. Проверки меняются по принятому контракту, а не ради заранее зелёного результата.

### S-9: Change без первоначальной SRS

Два завершённых change не связаны с SRS и остаются вне архива без ошибки за отсутствие SRS. Отдельная задача готовит первоначальную SRS по актуальным принятым обязательствам обоих changes, учитывая последовательное изменение одного поведения. Старые комплекты не переписываются; происхождение сохраняется в новой SRS. Подготовка самой SRS продукта не выполняется этим change — проверяется только изолированный пример.

### S-10: Актуальная форма и архив

Неархивный документ с недостающим разделом получает предупреждение о текущей форме; такой же архивный документ не требует добавления раздела и не изменяется. Архив продолжает участвовать в поиске адресатов и уникальности ID. Битый YAML, неоднозначный ID и повреждённые текущие ссылки не маскируются предупреждением о старой форме. Проверка показывает свой охват, не заявляя соответствия архивных документов актуальному шаблону.

## Definition of Done

Выполнены AC и сценарии S-1–S-10. Применимые проверки документации, TypeScript, общего индекса и поставки выбраны по `AGENTS.md`. Результаты и границы доказательности сохранены в Journal; фактические изменения соответствуют `scope`.
